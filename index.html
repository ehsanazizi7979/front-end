Chapter 1: What Is JavaScript?

From You Don’t Know JS Yet: Get Started (2nd Edition, 2020) by Kyle Simpson · Book pp. 12–41

Chapter in 30 Seconds:
  • One standard language: JavaScript is an implementation of ECMAScript (ES2019 as of writing), stewarded by TC39 and ECMA—not related to Java.
  • Multi-paradigm & backwards-compatible: Mixes procedural, OO, and functional styles; 1995 code still works today, while transpilers (Babel) and polyfills bridge newer features to older engines.
  • Compiled, not merely scripted: JS engines parse source into an AST, compile to bytecode + JIT-optimize, report static/early errors up front, and default to strict mode in modern modules/builds.

1. About This Book

Book pp. 12–13

Kyle Simpson opens with a humbling premise: none of us know JS completely, yet. Knowing JavaScript is not a fixed destination—it is an ongoing journey and direction that rewards patience, persistence, and hands-on coding.

Crucially, even though the book is titled Get Started, it is not a beginner/introductory programming book. It assumes several months of prior JS familiarity and builds the conceptual map required before diving into the deeper volumes of the YDKJSY series.

2. What’s With That Name?

Book pp. 13–15

“JavaScript” is arguably the most misunderstood name in programming. When Brendan Eich created the language, he code-named it Mocha, and Netscape briefly used LiveScript internally. The public name JavaScript won purely as a marketing ploy to attract Java programmers and position it as a lightweight “script” companion for web pages (it could just as easily have been called “WebJava”).

Any superficial syntax resemblance to Java—such as { and } for blocks and ; to end statements—comes from both languages targeting developers familiar with C and C++ syntax, not from shared lineage. Legally, Oracle (via Sun) still owns the “JavaScript” trademark (originally via Netscape), though it is essentially unenforced.

To distance the language from the trademark, the official standard name maintained by TC39 and formalized by ECMA is ECMAScript. Since 2016, revisions are named by year (e.g., ECMAScript 2019 / ES2019). Browser JS and Node.js are implementations of that standard.

Note (Book p. 15)

Don’t use terms like “JS6” or “ES8” to refer to the language. Some do, but those terms only serve to perpetuate confusion. “ES20xx” or just “JS” are what you should stick to.

“Java is to JavaScript as ham is to hamster.” — Jeremy Keith, 2009

3. Language Specification

Book pp. 15–22

JavaScript’s syntax and behavior are governed by the ECMAScript specification (ecma-262; ES2019 is revision 10.0). The technical steering committee TC39—50 to ~100 volunteer representatives from browser and device makers (Mozilla, Google, Apple, Samsung, etc.)—meets roughly every other month to debate and vote on changes.

Every new feature advances through a 0-indexed five-stage pipeline on GitHub (tc39/proposals): from Stage 0 (championed by a TC39 member; informal blog/social-media ideas are “pre-stage 0”) up to Stage 4 (ready for the next yearly release), often taking months to years.

One JS, Not Multiple Versions

Unlike the early 2000s when Microsoft maintained an incompatible fork called JScript, there are not multiple versions of JS in the wild today. All major engines—such as Chrome’s V8 and Mozilla’s SpiderMonkey—implement the same single specification (merely shipping new features on different schedules).

The Web Rules Everything About (JS)

Although JS runs on servers (Node.js), robots, and IoT devices, web browsers dictate practical reality. If a proposed spec change breaks existing websites, engines refuse it and TC39 adapts the spec:

  • Planned Array.prototype.contains(..) conflicted with legacy frameworks, so it became includes(..).
  • In “smooshgate,” planned flatten(..) was renamed flat(..).
  • Appendix B (“Additional ECMAScript Features for Web Browsers”) isolates web-only historical quirks (e.g., 0-prefixed octal literals, escape(..)/unescape(..), String#anchor(..)/blink(), RegExp#compile(..)) that non-web JS engines must avoid.

Not All (Web) JS… & It’s Not Always JS

Many familiar “JS” functions are actually host/environment APIs injected into global scope—not part of the ECMAScript specification. Consider this snippet from the book:

Book Code · p. 19 — Host/Environment API Example 
alert("Hello, JS!");

alert(..), fetch(..), getCurrentLocation(..), getUserMedia(..), Node’s fs.write(..), and even console.log(..) are “guests” that obey JS syntax while their behavior is provided by the host environment. Most complaints that “JS is inconsistent across browsers” actually stem from host API differences, not JS itself.

Similarly, browser Developer Tools consoles / REPLs optimize for DX (Developer Experience) rather than strict spec fidelity—exhibiting quirks around top-level var/function vs window, multiple let/const declarations, "use strict"; persistence across entries, non-strict this binding, and hoisting. Treat consoles as “JS-friendly” scratchpads, not the exact language spec.

4. Many Faces

Book pp. 22–23

A programming paradigm is an overarching mindset for structuring code. Whereas C leans procedural, Java/C++ lean class-oriented, and Haskell is purely functional, JavaScript is a multi-paradigm language. Developers can mix and match styles on a line-by-line basis:

Procedural

Organizes code as a top-down, linear progression through predetermined steps grouped into procedures.

Object-Oriented (OO / Classes)

Groups data and logic together into cohesive units called classes and instances.

Functional (FP)

Organizes programs around pure function computations and treats functions themselves as values.

5. Backwards & Forwards

Book pp. 24–31

JS is built on an extraordinary commitment to backwards compatibility (“we don’t break the web!”): once syntax or behavior is valid JS, code written as far back as 1995 should continue working in modern engines. The trade-off is that design mistakes become effectively permanent, making TC39 extremely cautious (breaking changes happen only rarely in tiny corner cases after browser telemetry).

However, JS is NOT forwards-compatible. Unlike declarative HTML and CSS—where older browsers gracefully skip unrecognized tags or rules—skipping unknown imperative JS statements or expressions would cause non-deterministic chaos. Running ES2019 syntax in a 2016 engine throws a compile-time syntax error; calling a missing newer API throws a runtime exception.

Jumping the Gaps: Transpiling

To write clean, modern syntax while supporting older engines, developers use a transpiler (most commonly Babel) to convert newer syntax into older equivalent source code. For example, block-scoped let code written by the developer:

Book Code · p. 27 — Authored ES6+ Source 
if (something) {
    let x = 3;
    console.log(x);
}
else {
    let x = 4;
    console.log(x);
}
Book Code · p. 27 — Babel-Transpiled Output 
var x$0, x$1;
if (something) {
    x$0 = 3;
    console.log(x$0);
}
else {
    x$1 = 4;
    console.log(x$1);
}
Note (Book p. 28)

The let keyword was added in ES6 (2015), so transpiling it is only needed for pre-ES6 environments. The transpilation target is a sliding window that moves upward as teams drop legacy browsers—while developers keep writing clean, modern JS.

Filling the Gaps: Polyfilling (Shimming)

When the compatibility gap is a missing API method rather than syntax, a polyfill (aka “shim”) provides a stand-in implementation for older engines. Consider ES2019’s Promise.prototype.finally(..):

Book Code · p. 29 — Using ES2019 Promise.prototype.finally(..) 
// getSomeRecords() returns us a promise for some
// data it will fetch
var pr = getSomeRecords();

// show the UI spinner while we get the data
startSpinner();

pr
.then(renderRecords)    // render if successful
.catch(showError)       // show an error if not
.finally(hideSpinner)   // always hide the spinner

A conceptual polyfill checks whether the method exists first, skipping itself in modern engines and defining it in older ones:

Book Code · p. 30 — Conceptual Polyfill for finally(..) 
if (!Promise.prototype.finally) {
    Promise.prototype.finally = function f(fn){
        return this.then(
            function t(v){
                return Promise.resolve( fn() )
                    .then(function t(){
                        return v;
                    });
            },
            function c(e){
                return Promise.resolve( fn() )
                    .then(function t(){
                        throw e;
                    });
            }
        );
    };
}
Warning (Book p. 30)

This is only a simple illustration of a basic (not entirely spec-compliant) polyfill for finally(..). Don’t use this polyfill in your code; always use a robust, official polyfill wherever possible, such as the collection of polyfills/shims in ES-Shim.

6. What’s in an Interpretation?

Book pp. 31–38

JS is widely mislabeled as a purely “interpreted scripting language” simply because source code (not precompiled binaries) is shipped to browsers. Simpson argues that the real distinction that matters is when errors are detected.

In a traditional line-by-line interpreted language, there is no upfront pass—an error on line 5 is only discovered after lines 1–4 have already executed:

By contrast, the ECMAScript specification requires JS to detect early errors (such as broken syntax or duplicate parameter names) before any execution begins. That requires a full parsing step into an Abstract Syntax Tree (AST), followed by code generation into binary bytecode, optimization by a JIT (Just-In-Time) compiler, and execution inside the JS Virtual Machine (just like Java on the JVM):

Putting the entire modern pipeline together from editor to execution yields four stages:

  1. Build toolchain: Source code is transpiled (e.g., Babel) and bundled (e.g., Webpack) before delivery to a JS engine.
  2. Parsing: The JS engine parses the delivered code into an AST.
  3. Compilation & JIT: The engine converts the AST into a binary intermediate representation (bytecode), refined further by optimizing JIT passes.
  4. Execution: The JS VM executes the compiled program.

Therefore, in spirit if not in practice, JS is a compiled language—giving developers upfront static error checking before partial execution occurs.

WebAssembly (WASM)

Performance demands led Mozilla in 2013 to demonstrate Unreal 3 running at 60fps in JS via ASM.js (a strictly typed, tool-generated subset of JS). That inspired WebAssembly (WASM): an assembly-like binary format compiled ahead of time (AOT) from statically typed languages (C, Go, etc.) that skips JS parsing/compilation in the engine.

WASM relieves pressure to bloat JS with features needed only by other languages (e.g., Go-style threads), and is even growing into a cross-platform VM outside the web. Dynamic JS/TS are not ideal sources for WASM (though AssemblyScript explores that bridge). Most importantly: WASM augments the web and will NOT replace JavaScript.

7. Strictly Speaking

Book pp. 38–41

Introduced in ES5 (2009), strict mode is an opt-in guide (not a “restriction”) that helps teams avoid silent bugs and gives JS engines the best chance to optimize code. It catches issues as compile-time early errors (like duplicate parameter names) and tightens runtime semantics (e.g., this defaults to undefined instead of the global object).

Enable strict mode per file using the "use strict"; pragma, with only whitespace or comments allowed before it:

Book Code · p. 39 — File-Level Strict Mode Pragma 
// only whitespace and comments are allowed
// before the use-strict pragma
"use strict";

// the rest of the file runs in strict mode
Warning (Book p. 40)

Even a stray ; all by itself before the strict mode pragma renders the pragma useless—no error is thrown (since a string literal in statement position is valid JS), yet strict mode silently fails to activate!

Alternatively, strict mode can be enabled per function—though you cannot mix file-level and function-level pragmas, and per-function mode is only justified when gradually migrating legacy non-strict files:

Book Code · p. 40 — Per-Function Strict Mode Pragma 
function someOperations() {
    // whitespace and comments are fine here
    "use strict";

    // all this code will run in strict mode
}

Because of backwards compatibility, strict mode will likely never become the technical default for plain scripts. Yet in practice it is already the de facto default: nearly all transpiled production bundles emit strict mode, and ES6 modules automatically run in strict mode.

8. Defined & Quick Reference

Book p. 41

Simpson closes Chapter 1 with a crisp definition of JavaScript:

  • Standardized: An implementation of the ECMAScript specification (ES2019 as of writing), guided by TC39 and hosted by ECMA, running in browsers, Node.js, and beyond.
  • Multi-paradigm: Seamlessly blends procedural, object-oriented (OO/classes), and functional (FP) patterns.
  • Compiled: Parsed, verified for early static errors, compiled/JIT-optimized, and executed by a JS virtual machine.

Chapter 1 Comparison Cheat Sheet

Concept Pair Key Distinction from Chapter 1
ECMAScript vs. Host APIs ECMAScript defines core JS syntax/behavior; alert(..), console.log(..), fetch(..), and fs.write(..) are host APIs provided by browsers or Node.js.
Backwards vs. Forwards Compatibility JS is backwards-compatible (1995 code still works), but not forwards-compatible (older engines reject newer syntax/APIs, unlike declarative HTML/CSS).
Transpiler vs. Polyfill Transpilers (Babel) rewrite newer syntax (e.g., let) into older syntax; polyfills (ES-Shim) implement missing newer APIs (e.g., Promise.prototype.finally).
Interpreted vs. Compiled Pure interpreters run line-by-line until failure; JS parses to an AST, enforces early errors, and compiles to bytecode + JIT before/during VM execution.

9. Each File is a Program

Book pp. 43–44

Even though a web application feels like one unified program, JS treats every standalone .js file as its own separate program. This distinction matters primarily for error handling: if one file fails during parse/compile or runtime, subsequent files can still be processed (though the overall app may only work partially).

Multiple standalone files act together at runtime by sharing state and functions via the global scope. Since ES6, JS also supports ES modules (loaded via import or <script type="module">); each module file is likewise treated individually and interoperates with others through explicit import links.

Note (Book p. 43)

Many projects use build tools (bundlers) to combine separate source files into a single output file delivered to a web page. When that happens, JS treats that single combined file as the entire program.

10. Values & Type Determination

Book pp. 44–50

A value is the fundamental unit of data/state in a program. JS values fall into two categories: primitives and objects, embedded into code as literals:

Book Code · p. 44 — Primitive String Literal 
greeting("My name is Kyle.");

Strings & Interpolation

Double quotes ("...") and single quotes ('...') are purely stylistic—pick one and stay consistent. Backticks (`...`), however, enable string interpolation (${ .. }); reserve backticks specifically for strings that interpolate expressions:

Book Code · pp. 45–46 — Quotes vs. Backtick Template Interpolation 
console.log("My name is ${ firstName }.");
// My name is ${ firstName }.

console.log('My name is ${ firstName }.');
// My name is ${ firstName }.

console.log(`My name is ${ firstName }.`);
// My name is Kyle.

console.log(
    `Am I confusing you by omitting interpolation?`
);
// Am I confusing you by omitting interpolation?

Booleans, Numbers, Empty Values, and Symbols

Other primitives include booleans (true / false), numbers (plus bigint for arbitrarily large integers, and predefined constants like Math.PI), the empty values null and undefined (Simpson recommends standardizing on undefined), and symbols (hidden, unguessable special object keys mostly used in libraries/frameworks):

Book Code · pp. 46–47 — Other Primitive Literals & Expressions 
while (false) {
    console.log(3.141592);
}

console.log(`My name is ${ names[1] }.`);
// My name is Kyle.

while (value != undefined) {
    console.log("Still got something!");
}

hitchhikersGuide[ Symbol("meaning of life") ];
// 42

Arrays and Objects

Arrays are a special sub-type of object storing an ordered, 0-indexed list of any value types (including other arrays and functions). General objects are unordered, keyed collections accessed via dot (name.first) or bracket (name["first"]) notation:

Book Code · p. 48 — Arrays 
names = [ "Frank", "Kyle", "Peter", "Susan" ];

names.length;
// 4

names[0];
// Frank

names[1];
// Kyle
Book Code · p. 49 — Objects 
name = {
    first: "Kyle",
    last: "Simpson",
    age: 39,
    specialties: [ "JS", "Table Tennis" ]
};

console.log(`My name is ${ name.first }.`);
Note (Book p. 48)

Functions, like arrays, are a special kind (sub-type) of object in JS.

Value Type Determination (typeof)

The typeof operator returns a string naming a primitive’s built-in type, or "object" otherwise (with two famous quirks):

Book Code · p. 49 — Using the typeof Operator 
typeof 42;                  // "number"
typeof "abc";               // "string"
typeof true;                // "boolean"
typeof undefined;           // "undefined"
typeof null;                // "object" -- oops, bug!
typeof { "a": 1 };          // "object"
typeof [1,2,3];             // "object"
typeof function hello(){};  // "function"
Warning (Book p. 49)

typeof null unfortunately returns "object" instead of the expected "null". Also, typeof returns the specific "function" for functions, but not the expected "array" for arrays.

11. Declaring and Using Variables

Book pp. 50–54

Variables (identifiers) act as containers for values and must be declared before use. JS offers multiple declaration forms with distinct scoping rules:

Book Code · p. 50 — var Declaration 
var name = "Kyle";
var age;
Book Code · p. 50 — let Declaration 
let name = "Kyle";
let age;

While var is function- or globally scoped, let creates block-scoped variables confined to their enclosing { .. } block—preventing accidental name collisions:

Book Code · p. 51 — Function/Outer Scoping (var) vs. Block Scoping (let) 
var adult = true;

if (adult) {
    var name = "Kyle";
    let age = 39;
    console.log("Shhh, this is a secret!");
}

console.log(name);
// Kyle

console.log(age);
// Error!
Note (Book p. 52)

Simpson pushes back against blanket “never use var” advice: var clearly communicates “this variable will be seen by a wider scope,” and both var and let have legitimate places when used deliberately.

const: Non-Reassignable, Not Immutable

const behaves like let except it must be initialized immediately and cannot be re-assigned. Crucially, objects/arrays held by a const variable can still be mutated, which can mislead readers:

Book Code · p. 52 — const Prevents Re-assignment 
const myBirthday = true;
let age = 39;

if (myBirthday) {
    age = age + 1;    // OK!
    myBirthday = false;  // Error!
}
Book Code · p. 53 — const Allows Object/Array Mutation 
const actors = [
    "Morgan Freeman", "Jennifer Aniston"
];

actors[2] = "Tom Cruise";   // OK :(
actors = [];                // Error!
Tip (Book p. 53)

If you stick to using const only with primitive values (giving readable names to constants like myBirthday), you avoid any confusion between re-assignment (disallowed) and mutation (allowed).

Other Identifier Declarations: Functions & catch Clauses

Function declarations create a function-scoped identifier in their enclosing scope (and parameter identifiers scoped inside the function), while catch (err) creates a block-scoped variable available only inside the catch block:

Book Code · p. 53 — Function & Parameter Scope 
function hello(name) {
    console.log(`Hello, ${ name }.`);
}

hello("Kyle");
// Hello, Kyle.
Book Code · p. 54 — catch Clause Block Scope 
try {
    someError();
}
catch (err) {
    console.log(err);
}

12. Functions

Book pp. 54–57

In JS, think of a “function” in the broader sense of a procedure: a collection of statements that can be invoked one or more times, accept parameter inputs, and return a single output (wrap multiple outputs in an object or array). Crucially, functions are values (a sub-type of object) that can be assigned to variables, passed around, and stored as object properties.

A function declaration associates its identifier with the function during the compile phase, whereas a function expression associates its variable only when that statement runs at runtime:

Book Code · p. 54 — Function Declaration 
function awesomeFunction(coolThings) {
    // ..
    return amazingStuff;
}
Book Code · p. 55 — Function Expression 
// let awesomeFunction = ..
// const awesomeFunction = ..
var awesomeFunction = function(coolThings) {
    // ..
    return amazingStuff;
};
Book Code · pp. 55–56 — Parameters & Return Values 
function greeting(myName) {
    console.log(`Hello, ${ myName }!`);
}

greeting("Kyle");   // Hello, Kyle!

function greeting(myName) {
    return `Hello, ${ myName }!`;
}

var msg = greeting("Kyle");
console.log(msg);   // Hello, Kyle!
Book Code · p. 56 — Functions as Object Properties 
var whatToSay = {
    greeting() {
        console.log("Hello!");
    },
    question() {
        console.log("What's your name?");
    },
    answer() {
        console.log("My name is Kyle.");
    }
};

whatToSay.greeting();
// Hello!

13. Comparisons & Coercion

Book pp. 57–64

Equal…ish (===, NaN, -0, and Object Identity)

The triple-equals (===) operator is often called “strict equality” and described as “checking both value and type.” More accurately, all JS comparisons consider types—what === specifically does is disallow type coercion:

Book Code · p. 58 — Triple-Equals (===) Examples 
3 === 3.0;              // true
"yes" === "yes";        // true
null === null;          // true
false === false;        // true

42 === "42";            // false
"hello" === "Hello";    // false
true === 1;             // false
0 === null;             // false
"" === null;            // false
null === undefined;     // false
Note (Book p. 58)

All value comparisons in JS consider the type of the values being compared—not just ===. The real difference is that === disallows any type conversion (“coercion”), whereas == and relational operators allow it.

However, === is not purely exact—it is designed to lie in two special cases: NaN and -0. Use Number.isNaN(..) for NaN and Object.is(..) (the “quadruple-equals” ====) for -0 or non-lying equality checks:

Book Code · p. 59 — The Two Lies of === 
NaN === NaN;            // false (use Number.isNaN(..) or Object.is(..))
0 === -0;               // true  (use Object.is(..))

For object values (arrays, plain objects, functions), === does not perform structural (content) equality—it performs reference identity equality. Two separate objects with identical contents are not ===; only two references pointing to the exact same object instance match:

Book Code · p. 59 — Distinct Object Literals Fail === 
[ 1, 2, 3 ] === [ 1, 2, 3 ];    // false
{ a: 42 } === { a: 42 }         // false
(x => x * 2) === (x => x * 2)   // false
Book Code · p. 60 — Reference Identity Comparison 
var x = [ 1, 2, 3 ];

// assignment is by reference-copy, so
// y references the *same* array as x,
// not another copy of it.
var y = x;

y === x;              // true
y === [ 1, 2, 3 ];    // false
x === [ 1, 2, 3 ];    // false

Coercive Comparisons (== and <, >, <=, >=)

Coercion converts a value from one type to another and is one of JS’s core pillars. When comparing values of the same type, == and === behave identically. When types differ, == (better termed coercive equality than “loose equality”) prefers converting non-numbers to numbers before performing an equality check.

Even if you avoid ==, you still encounter coercion in relational operators (<, >, <=, >=), which coerce mismatched operands to numbers—except when both operands are already strings, in which case they compare alphabetically!

Book Code · p. 62 — Coercive Equality (==) 
42 == "42";             // true
1 == true;              // true
Book Code · p. 63 — Relational Coercion & String Ordering 
var arr = [ "1", "10", "100", "1000" ];
for (let i = 0; i < arr.length && arr[i] < 500; i++) {
    // will run 3 times
}

var x = "10";
var y = "9";

x < y;          // true, watch out!

14. How We Organize in JS: Classes & Modules

Book pp. 64–77

Two major patterns organize data and behavior across JS codebases: classes and modules. They are not mutually exclusive—though in many ways they represent two sides of the same coin.

Classes & Class Inheritance

A class defines a custom data structure bundling data and methods; concrete instances are created with new. With extends and super(..), child classes inherit from parent classes and can override methods (polymorphism) while still delegating to super.print():

Book Code · p. 65 — Page & Notebook Classes 
class Page {
    constructor(text) {
        this.text = text;
    }

    print() {
        console.log(this.text);
    }
}

class Notebook {
    constructor() {
        this.pages = [];
    }

    addPage(text) {
        var page = new Page(text);
        this.pages.push(page);
    }

    print() {
        for (let page of this.pages) {
            page.print();
        }
    }
}

var mathNotes = new Notebook();
mathNotes.addPage("Arithmetic: + - * / ...");
mathNotes.addPage("Trigonometry: sin cos tan ...");

mathNotes.print();
// ..
Book Code · pp. 67–69 — Inheritance & Polymorphism (Publication, Book, BlogPost) 
class Publication {
    constructor(title,author,pubDate) {
        this.title = title;
        this.author = author;
        this.pubDate = pubDate;
    }

    print() {
        console.log(`
            Title: ${ this.title }
            By: ${ this.author }
            ${ this.pubDate }
        `);
    }
}

class Book extends Publication {
    constructor(bookDetails) {
        super(
            bookDetails.title,
            bookDetails.author,
            bookDetails.publishedOn
        );
        this.publisher = bookDetails.publisher;
        this.ISBN = bookDetails.ISBN;
    }

    print() {
        super.print();
        console.log(`
            Publisher: ${ this.publisher }
            ISBN: ${ this.ISBN }
        `);
    }
}

class BlogPost extends Publication {
    constructor(title,author,pubDate,URL) {
        super(title,author,pubDate);
        this.URL = URL;
    }

    print() {
        super.print();
        console.log(this.URL);
    }
}

var YDKJS = new Book({
    title: "You Don't Know JS",
    author: "Kyle Simpson",

Classic modules predate ES6 syntax (sharing core principles with AMD, UMD, and CommonJS): an outer function returns a publicAPI object exposing methods that close over private scope variables—no this. prefix and no new keyword required, with true data privacy for unexposed variables:

            console.log(`
                Title: ${ title }
                By: ${ author }
                ${ pubDate }
            `);
        }

    return publicAPI;

16. Iteration & Iterables

Book pp. 79–85

Rather than loading an entire dataset (like 1,000+ database rows) at once, the iterator pattern standardizes consuming data progressively, one chunk at a time. In ES6, an iterator exposes a next() method returning an iterator result object { value, done }, where done stays false until traversal finishes.

Consuming Iterators (for..of and ... Spread)

Instead of manually calling next() in a loop, ES6 provides standardized iterator consumers: the for..of loop and the iterator-spread form of ... (spreading into an array literal or function call arguments):

Book Code · p. 80 — Consuming an Iterator with for..of 
// given an iterator of some data source:
var it = /* .. */;

// loop over its results one at a time
for (let val of it) {
    console.log(`Iterator value: ${ val }`);
}
// Iterator value: ..
// Iterator value: ..
// ..
Note (Book p. 81)

The manual next() loop equivalent is omitted because it’s far less readable than for..of.

Book Code · p. 81 — Array Spread 
// spread an iterator into an array,
// with each iterated value occupying
// an array element position.
var vals = [ ...it ];
Book Code · p. 81 — Function Call Spread 
// spread an iterator into a function,
// call with each iterated value
// occupying an argument position.
doSomethingUseful( ...it );

Iterables (Array, String, Map, keys(), values(), entries())

An iterable is a value that can be iterated over—each time the protocol runs on an iterable, it creates and consumes a fresh iterator instance. Built-in ES6 iterables include arrays, strings, maps, and sets:

Book Code · p. 82 — Iterating & Shallow-Copying Arrays 
// an array is an iterable
var arr = [ 10, 20, 30 ];

for (let val of arr) {
    console.log(`Array value: ${ val }`);
}
// Array value: 10
// Array value: 20
// Array value: 30

var arrCopy = [ ...arr ];
Book Code · p. 83 — Iterating Characters of a String 
var greeting = "Hello world!";
var chars = [ ...greeting ];

chars;
// [ "H", "e", "l", "l", "o", " ",
//   "w", "o", "r", "l", "d", "!" ]

A Map uses objects as keys and defaults to iterating over [key, value] entry tuples (conveniently unpacked via array destructuring). Built-in iterables also expose explicit keys(), values(), and entries() iterators:

Book Code · p. 83 — Iterating a Map with Destructuring 
// given two DOM elements, `btn1` and `btn2`

var buttonNames = new Map();
buttonNames.set(btn1,"Button 1");
buttonNames.set(btn2,"Button 2");

    btn.addEventListener("click",function onClick(){
        console.log(`Clicked ${ btnName }`);
    });
}
Book Code · p. 84 — Map .values() 
for (let btnName of buttonNames.values()) {
    console.log(btnName);
}
// Button 1
// Button 2
Book Code · p. 84 — Array .entries() 
var arr = [ 10, 20, 30 ];

for (let [idx,val] of arr.entries()) {
    console.log(`[${ idx }]: ${ val }`);
}
// [0]: 10
// [1]: 20
// [2]: 30
Note (Book p. 85)

The iteration-consumption protocol expects an iterable, yet passing a direct iterator also works because an iterator is an iterable of itself (creating an iterator from an existing iterator simply returns itself).

17. Closure

Book pp. 85–89

Simpson gives a concrete, pragmatic definition of one of JS’s most fundamental concepts:

“Closure is when a function remembers and continues to access variables from outside its scope, even when the function is executed in a different scope.” — Kyle Simpson, Book p. 85

Two defining traits stand out: (1) functions get closures (objects don’t), and (2) you observe closure when a function executes in a different scope from where it was defined. Importantly, closure is a live link to the variable itself—not a static snapshot of its value—so updates over time are preserved and observed.

Book Code · p. 86 — Preserving Outer Variables 
function greeting(msg) {
    return function who(name) {
        console.log(`${ msg }, ${ name }!`);
    };
}

var hello = greeting("Hello");
var howdy = greeting("Howdy");

hello("Kyle");      // Hello, Kyle!
hello("Sarah");     // Hello, Sarah!
howdy("Grant");     // Howdy, Grant!
Book Code · p. 87 — Live Link & State Updates 
function counter(step = 1) {
    var count = 0;
    return function increaseCount(){
        count = count + step;
        return count;
    };
}

var incBy1 = counter(1);
var incBy3 = counter(3);

incBy1();   // 1
incBy1();   // 2

incBy3();   // 3
incBy3();   // 6
incBy3();   // 9

Closure appears constantly in asynchronous callbacks (preserving variables after the outer function returns) and in block-scoped loops (each iteration’s let creates a fresh variable for the event handler to close over):

Book Code · p. 88 — Async Callback Closure 
function getSomeData(url) {
    ajax(url,function onResponse(resp){
        console.log(
            `Response (from ${ url }): ${ resp }`
        );
    });
}

getSomeData("https://some.url/wherever");
// Response (from https://some.url/wherever): ...
Book Code · p. 88 — Per-Iteration let Loop Closure 
for (let [idx,btn] of buttons.entries()) {
    btn.addEventListener("click",function onClick(){
        console.log(`Clicked on button (${ idx })!`);
    });
}

18. The this Keyword

Book pp. 89–92

Contrary to popular myths, this does not point to the function itself, nor is it fixed to the object where a method was defined. While lexical scope is static and fixed at function definition, this represents a dynamic execution context determined each time the function is called.

Book Code · p. 90 — A this-Aware Function Inside a Closure 
function classroom(teacher) {
    return function study() {
        console.log(
            `${ teacher } says to study ${ this.topic }`
        );
    };
}

var assignment = classroom("Kyle");
Note (Book p. 90)

study() is simultaneously closed over the static teacher variable from its outer scope and aware of its dynamic this execution context.

Calling the exact same assignment function in three different ways binds this to three different objects:

p. 91 — Default (Non-Strict Global) 
assignment();
// Kyle says to study undefined  -- Oops :(
p. 91 — Object Method Call 
var homework = {
    topic: "JS",
    assignment: assignment
};

homework.assignment();
// Kyle says to study JS
p. 92 — Explicit .call(..) 
var otherHomework = {
    topic: "Math"
};

assignment.call(otherHomework);
// Kyle says to study Math

19. Prototypes & this Revisited

Book pp. 92–98

Whereas this is a characteristic of function execution, a prototype is a hidden linkage between objects ([[Prototype]]) that resolves property accesses. When object B lacks a property or method, JS delegates the lookup up the prototype chain to object A—which is why any plain object literal automatically inherits toString() and valueOf() from Object.prototype:

Book Code · p. 93 — Default Delegation to Object.prototype 
var homework = {
    topic: "JS"
};

homework.toString();    // [object Object]

Object Linkage (Object.create(..)) & Shadowing

Use Object.create(homework) to create a new object prototype-linked directly to homework:

Book Code · p. 94 — Linking Objects with Object.create(..) 
var homework = {
    topic: "JS"
};

var otherHomework = Object.create(homework);

otherHomework.topic;    // "JS"
Tip (Book p. 95)

Object.create(null) creates a purely standalone object with no prototype linkage at all—useful when you want a clean dictionary without inherited properties.

Prototype delegation only applies to reading/looking up properties. Assigning to otherHomework.topic = "Math" creates a new property directly on otherHomework—shadowing homework.topic without modifying it:

Book Code · p. 95 — Property Assignment Shadows Instead of Mutating Prototype 
homework.topic;                 // "JS"
otherHomework.topic;            // "JS"

otherHomework.topic = "Math";
otherHomework.topic;            // "Math"
homework.topic;                 // "JS" -- not "Math"
Note (Book p. 96)

Pre-ES6 code often constructed prototype linkages using the more convoluted “prototypal class” pattern (covered in Appendix A, Prototypal “Classes”).

this Revisited: Powering Prototype Delegation

The true purpose of JS’s dynamic this shines when combined with prototypes: even though study() is defined only once on homework, calling jsHomework.study() or mathHomework.study() delegates the method lookup up the chain while keeping this bound to the respective calling child object!

Book Code · p. 97 — Dynamic this + Prototype Delegation 
var homework = {
    study() {
        console.log(`Please study ${ this.topic }`);
    }
};

var jsHomework = Object.create(homework);
jsHomework.topic = "JS";
jsHomework.study();
// Please study JS

var mathHomework = Object.create(homework);
mathHomework.topic = "Math";
mathHomework.study();
// Please study Math

21. Pillar 1: Scope and Closure

Book pp. 101–102

Organizing variables into units of scope (functions and blocks) is one of the most foundational characteristics of any language—perhaps nothing else shapes program behavior more. Simpson frames scope using the buckets and marbles analogy: scopes are colored buckets, variables are marbles, and scope rules decide which marbles belong in which matching buckets.

Scopes nest inside one another. Any expression or statement can access variables in its own scope or in higher/outer scopes, while variables in lower/inner scopes remain hidden and inaccessible. This is lexical scope: scope boundaries and variable organization are determined when the program is parsed/compiled (an author-time decision based on where functions and blocks are written).

Hoisting & Function var

Variables declared anywhere in a scope act as if declared at its start, and var is function-scoped even inside blocks. Neither invalidates lexical scope.

Temporal Dead Zone (TDZ)

let and const create observable-but-unusable variables before their declaration line—peculiar, yet still strictly lexical.

Closure & Modules

Lexical scope + first-class functions produce closure, powering vital JS patterns—especially modules, which are as with the grain of JS as code organization gets.

Next step for this pillar: Read Book 2, Scope & Closures, to explore lexical scope, closures, and the module pattern in depth.

22. Pillar 2: Prototypes

Book pp. 102–103

JS is one of very few languages where you can create objects directly and explicitly without first defining their structure in a class. Historically, developers layered class patterns onto prototypes (“prototypal inheritance,” covered in Appendix A), and ES6’s class keyword doubled down on OO/class-style programming.

That heavy focus on classes—alongside functional programming (FP) as the “anti-class” alternative—obscures the real beauty and power of JS’s prototype system: two objects simply connecting and cooperating dynamically during method execution by sharing a this context.

  • Behavior Delegation: Embracing objects as objects—forgetting classes altogether and letting objects cooperate across the prototype chain. Simpson argues delegation is more powerful than class inheritance for organizing behavior and data.
  • Not anti-class, just broader perspective: Classes are only one pattern built atop prototypes; object delegation is far more with the grain of JS.

Next step for this pillar: Read Book 3, Objects & Classes, to see how object delegation unlocks capabilities beyond traditional classes.

23. Pillar 3: Types and Coercion

Book pp. 104–105

The third pillar is the most overlooked part of JS’s nature. Widespread misconceptions about how types work in JS have fueled a surge toward external “static typing” tools like TypeScript and Flow.

While type-aware tooling can certainly help developers after they understand JS’s own type system, Simpson pushes back against treating JS’s type mechanism as broken or trying to cover it up with external tools. Going against the crowd—and with the grain of JS—means mastering how JS manages value types and conversions natively.

  • Arguably the most important pillar: No JS program does anything useful without properly leveraging JS’s value types and type conversions (coercion).
  • Essential even for TypeScript/Flow users: You cannot get the most out of static-typing tools unless you deeply understand how JS itself handles value types at runtime.
  • Look past dogma: Don’t skip coercion just because you’ve always heard “use === and forget the rest”—without this pillar, your JS foundation remains shaky and incomplete.

Next step for this pillar: Read Book 4, Types & Grammar, to build a complete command of JS types, coercion, and syntax.

26. Values vs. References

Book pp. 110–112

In many languages, the developer chooses whether to assign or pass a value itself or a reference to it. In JavaScript, that choice is determined strictly by the kind of value, and cannot be overridden in either direction:

  • Primitives (held & copied by value): Assigning or passing a primitive creates an independent copy of that value.
  • Objects (held & copied by reference): Arrays, objects, and functions are held by reference; assigning one variable to another copies the reference to the same shared object, so mutating properties through one reference is visible through all of them.
Book Code · pp. 110–111 — Primitive Value Copy 
var myName = "Kyle";
var yourName = myName;

myName = "Frank";

console.log(myName);
// Frank

console.log(yourName);
// Kyle

    street: "123 JS Blvd",

    state: "TX"

// I've got to move to a new house!

27. So Many Function Forms

Book pp. 112–117

An anonymous function expression has no identifier between function and (..). Since ES6, JS performs name inference when an anonymous function is assigned (e.g., with =), populating its .name metadata property for dev tools and stack traces. However:

  • Passing an anonymous function directly as an argument triggers no name inference (.name is "", shown as (anonymous function)).
  • Even when inferred, the function is still anonymous—it has no internal identifier to reference itself (for recursion, event unbinding, etc.).
  • With a named function expression, the explicit name binds at compile time, takes precedence on .name, and saves future readers from having to mentally execute the body (even for x * 2) to figure out what the function does.
Book Code · p. 113 — Anonymous Function Expression 
var awesomeFunction = function(coolThings) {
    // ..
    return amazingStuff;
};

awesomeFunction.name;
// "awesomeFunction"
Book Code · p. 114 — Named Function Expression 
// let awesomeFunction = ..
// const awesomeFunction = ..
var awesomeFunction = function someName(coolThings) {
    // ..
    return amazingStuff;
};

awesomeFunction.name;
// "someName"

28. Coercive Conditional Comparison

Book pp. 117–119

Conditional expressions in if, ? : ternary statements, while, and for loops perform an implicit comparison that is both coercive and strict.

Thinking of if (x) as if (x == true) appears to work when x = 1, but fails when x = "hello" (where if (x) runs, yet x == true is false). The accurate mental model is: JS first coerces x to a boolean via Boolean(x), then compares against true (making == and === identical afterward):

Book Code · p. 118 — Implicit Conditionals (x = 1) 
var x = 1;

if (x) {
    // will run!
}

while (x) {
    // will run, once!
    x = false;
}

// Misleading mental model (works only for x = 1):
if (x == true) {
    // will run!
}

while (x == true) {
    // will run, once!
    x = false;

29. Prototypal “Classes” & Appendix A Cheat Sheet

Book pp. 120–122

Before ES6 introduced the class keyword, developers simulated class “inheritance” on top of prototypes using constructor functions and .prototype—the “ugly” predecessor known as prototypal classes.

Tip (Book p. 120)

While this style of code is quite uncommon in JS these days, it’s still perplexingly rather common to be asked about it in job interviews!

Every function by default references an empty object at Fn.prototype. Despite the confusing name, this is not the function’s own prototype—it is the prototype object that newly created objects will link to when the function is invoked with new. Today, ES6 class wires up the exact same prototype linkage far more cleanly (though it is strongly preferred over “prototypal classes”).

Book Code · p. 120 — Object.create(..) 
var Classroom = {
    welcome() {
        console.log("Welcome, students!");
    }
};

var mathClass = Object.create(Classroom);

mathClass.welcome();
// Welcome, students!

Appendix A Quick-Reference Cheat Sheet

Topic Key Nuance
Values vs. References Primitives copy by value; objects/arrays/functions copy by reference (shared object). JS determines this by value type—never developer syntax.
Function Forms & Names ES6 name inference sets .name on assignments, not callbacks, and doesn’t create a self-reference identifier. Prefer named functions; use => for lexical this.
Conditional Coercion if (x), while (x), for, and ? : evaluate Boolean(x) === true (not x == true).
Prototypal “Classes” new Fn() links the new object to Fn.prototype; know it for interviews, but use ES6 class (for class patterns) or Object.create(..) (for delegation).

const dayStart = "07:30";
const dayEnd = "17:45";

function scheduleMeeting(startTime,durationMinutes) {
    var [ , meetingStartHour, meetingStartMinutes ] =
        startTime.match(/^(\d{1,2}):(\d{2})$/) || [];

    durationMinutes = Number(durationMinutes);

    if (
        typeof meetingStartHour == "string" &&
        typeof meetingStartMinutes == "string"
    ) {
        let durationHours =
            Math.floor(durationMinutes / 60);
        durationMinutes =
            durationMinutes - (durationHours * 60);
        let meetingEndHour =
            Number(meetingStartHour) + durationHours;
        let meetingEndMinutes =
            Number(meetingStartMinutes) +
            durationMinutes;

        if (meetingEndMinutes >= 60) {
            meetingEndHour = meetingEndHour + 1;
            meetingEndMinutes =
                meetingEndMinutes - 60;
        }

        // re-compose fully-qualified time strings
        // (to make comparison easier)
        let meetingStart = `${
            meetingStartHour.padStart(2,"0")
        }:${
            meetingStartMinutes.padStart(2,"0")
        }`;
        let meetingEnd = `${
            String(meetingEndHour).padStart(2,"0")
        }:${
            String(meetingEndMinutes).padStart(2,"0")
        }`;

        // NOTE: since expressions are all strings,
        // comparisons here are alphabetic, but it's
        // safe here since they're fully qualified
        // time strings (ie, "07:15" < "07:30")
        return (
            meetingStart >= dayStart &&
            meetingEnd <= dayEnd
        );
    }

    return false;
}

scheduleMeeting("07:15",30);    // false

function range(start,end) {
    start = Number(start) || 0;

    if (end === undefined) {
        return function getEnd(end) {
            return getRange(start,end);
        };
    }
    else {
        end = Number(end) || 0;
        return getRange(start,end);
    }

    // **********************

    function getRange(start,end) {
        var ret = [];
        for (let i = start; i <= end; i++) {
            ret.push(i);
        }
        return ret;
    }
}

function randMax(max) {
    return Math.trunc(1E9 * Math.random()) % max;
}

var reel = {
    symbols: [
        "X", "Y", "Z", "W", "$", "*", "<", "@"
    ],
    spin() {
        if (this.position == null) {
            this.position = randMax(
                this.symbols.length - 1
            );
        }
        this.position = (
            this.position + 100 + randMax(100)
        ) % this.symbols.length;
    },
    display() {
        if (this.position == null) {
            this.position = randMax(
                this.symbols.length - 1
            );
        }
        return this.symbols[this.position];
    }
};

var slotMachine = {
    reels: [
        Object.create(reel),
        Object.create(reel),
        Object.create(reel)
    ],
    spin() {
        this.reels.forEach(function spinReel(reel){
            reel.spin();
        });
    },
    display() {
        var lines = [];

        // display all 3 lines on the slot machine
        for (
            let linePos = -1; linePos <= 1; linePos++
        ) {
            let line = this.reels.map(
                function getSlot(reel){
                    var slot = Object.create(reel);
                    slot.position = (
                        reel.symbols.length +
                        reel.position +
                        linePos
                    ) % reel.symbols.length;
                    return reel.display.call(slot);
                }
            );
            lines.push(line.join(" | "));
        }

        return lines.join("
");
    }
};

slotMachine.display();

// @ | X | <
// X | Y | @
