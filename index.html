What the chapter covers

JavaScript started life in 1995 as a ten-day project to add a scripting language to Netscape’s browser. Today it is one of the most widely used languages in the world: it runs websites, servers, mobile and desktop apps, game consoles, IoT devices — and, increasingly, your car. The chapter opens by asking how a single language made the leap from the browser to the wider world of computing. The answer, in one word: evolution.

For years JavaScript carried a reputation for being slow and quirky, with none of the comforts other languages offered — rich IDE integration, static analysis, debugging tools, a package distribution system. Developers tolerated it because it was the only language browsers ran, but few loved it. Three things changed that:

  • Competition between browser vendors produced dramatically faster engines.
  • Cooperation between them produced the ECMAScript standards process for new language features.
  • The Node.js runtime took JavaScript outside the browser and brought with it an entire package ecosystem and a toolchain written in JavaScript itself.

The chapter in three points:

  • What makes JavaScript special
  • How JavaScript evolves over time
  • Three best practices in JavaScript development

Thanks to that evolution, JavaScript is both enormously versatile and — for most purposes — reasonably performant. Developer experience improved too: the IDE integration and static analysis people once only dreamed about now arrive via TypeScript. TypeScript has become so popular that it is nearly synonymous with JavaScript development, and the authors admit they considered calling this book Secrets of the TypeScript Ninja. But TypeScript is just a tool for developing JavaScript, so the book integrates it in that spirit.

The book’s plan is to build understanding from the ground up — fundamentals first, then the “secret” techniques that separate the JavaScript Ninja from the ordinary developer.

1.1 Understanding the JavaScript language

A common trap: assuming that knowing C# or Java means you already understand JavaScript. Compared with other mainstream languages, JavaScript is far more functionally oriented, and several of its concepts differ fundamentally.

DifferenceWhat it meansWhere it’s covered
Functions are first-class objects Functions coexist with, and can be treated like, any other object: assigned to variables, passed as arguments, even created by other functions. Chapter 5
Prototype-based object orientation Unlike class-based languages (C#, Java, Ruby), JavaScript uses prototypes. It has a class keyword today, but under the hood those classes are defined in terms of prototypes. Chapter 9
Single-threaded Code runs on a single thread; asynchronous work relies on callbacks and promises, with workers available to move work off the main thread. Chapters 3, 8 and 14

JavaScript is really a set of close relationships: objects and prototypes, and functions and closures. Understanding those relationships is the foundation for any kind of application — browser, server or app.

On top of the fundamentals, the book covers language features that make code more elegant and efficient:

  • Promises — better control over asynchronous code.
  • Advanced array methods — much more elegant array handling.
  • Maps and sets — dictionary collections, and collections of unique items.
  • Regular expressions — simplify what would otherwise be complicated code.
  • Modules — break code into smaller, self-contained pieces that keep projects manageable.

1.1.1 JavaScript runtimes and engines

JavaScript’s popularity has taken it to browsers, servers, apps, consoles and devices, which means many runtimes — environments that execute JavaScript. Node.js is the best-known non-browser runtime, facing growing competition from Deno and Bun.

Under the hood every runtime uses an engine to convert JavaScript into machine instructions for the CPU. Modern engines use just-in-time (JIT) compilation to optimise code as it runs, and are continuously improved for speed and for new ECMAScript features. Two notable engines: V8 (Chrome and Node.js) and JavaScriptCore (Safari and Bun).

A runtime also supplies API bindings, which let your code interact with its host environment. In the browser you might fetch data over the network, listen for user events and update the DOM; in Node.js you might listen on a TCP socket, write to disk and spawn subprocesses.

Some code is deliberately cross-runtime — Lodash, for example, is used in browsers, servers and apps alike — while other code targets one runtime. Either way, code crosses over: Node.js can simulate a browser with jsdom (useful for testing or pre-rendering HTML), and browsers can simulate Node.js with WebContainers (useful for secure sandboxes and zero-install dev environments).

Note Most of the techniques in this book work in any modern JavaScript runtime, browser or standalone. The book flags exceptions as it goes. Node.js is the focus of Chapter 3 and browsers of Chapter 4 — and even browser-only developers will want Node.js for the development environment and build pipeline.

1.1.2 How does JavaScript get new features?

Shortly after Netscape introduced the language in 1995, a committee formed to standardise it. Because of Sun Microsystems’ trademark on the word “Java” — which Netscape was using under licence — that committee is now the ECMAScript Committee. In practice ECMAScript and JavaScript are synonyms: ECMAScript appears in official specifications, JavaScript is the popular name everywhere else.

For years the standard changed little, concentrating on consistent behaviour across implementations. That changed in 2015, when ES6 (later renamed ES2015) brought arrow functions, maps, promises, modules and much more. Since then a new standard has landed every year: ES2016, ES2017, and so on.

That steady drip of features is exciting, but it means you must know which features the runtimes you target actually support — especially on the web, where the runtime is the user’s possibly-ancient browser. Chapter 14 covers strategies for targeting a wide range of browsers, and the ECMAScript compatibility table shows which runtimes support a given feature.

1.1.3 Transpilers and polyfills give us access to tomorrow’s JavaScript today

You can use the newest features without waiting for universal support, in two complementary ways:

  • Transpiler (“transformation + compiler”) — rewrites cutting-edge code into a functionally equivalent form limited to older ECMAScript features. The idea was pioneered by Babel, and the TypeScript compiler also transpiles syntax down to a target ECMAScript version.
  • Polyfill — code that defines a feature in runtimes where it isn’t natively provided. Want promises (ES6) but must support Internet Explorer 11 (stuck on ES5)? A polyfill can define a global Promise with the same behaviour as the ES6 API.

Polyfills are often used together with transpilation — Babel can inject the needed polyfills while it transpiles; TypeScript doesn’t, which is one reason TypeScript and Babel are frequently paired.

Some features simply cannot be implemented efficiently in older runtimes. Regex lookbehind assertions, added in ES2018, are the example: in a runtime without that feature the regex fails, transpiled or not. So know which runtimes you target and what they support — and, better still, automate tests for those runtimes.

1.2 Navigating the world of frameworks

JavaScript’s open-source ecosystem puts millions of libraries at your fingertips, and choosing the right ones is a critical skill. For most projects the first question is: which framework?

A framework is a library that powers the core functionality of your application. A web app uses its framework to render HTML; a server app uses its framework to parse HTTP requests and send responses. You could build the same functionality yourself, but a well-chosen framework saves an enormous amount of time — nearly all modern JavaScript applications are built on one.

1.2.1 Web UI frameworks

Early JavaScript added a dash of interactivity to otherwise static sites: the browser downloaded and rendered a complete HTML document, then ran a script for enhancements such as form validation. The dominant frameworks — jQuery above all — were thin wrappers around browser APIs, smoothing over cross-browser differences. Complex web apps were awkward, because you bounced back and forth between HTML and JavaScript.

In the 2010s a new generation of frameworks let developers write HTML inside JavaScript. One of them, React, soon ruled the web, introducing JSX — a way to write JavaScript and HTML together that feels natural:

React component using JSXJSX
import React, {useState} from "react";

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <div>The count is {count}.</div>
      <button
        onClick={() => {
          setCount(count + 1);
        }}
      >
        Increment count
      </button>
    </div>
  );
}

Under the hood React uses a virtual DOM: it builds a tree describing what the page’s HTML should look like, compares that tree against the existing HTML, and then updates the page so the two match. That saves developers from touching the DOM directly. React has no shortage of challengers — Angular, Vue and Svelte among them — and many borrow JSX or a similar templating language, adding their own spin on React’s paradigm rather than overturning it. A key factor when choosing is the ecosystem: a newer framework may be more elegant and efficient, but React gives access to thousands of ready-made component libraries.

Note The JavaScript library world moves fast. One excellent resource for keeping up with browser-based JavaScript is Chen Cheng’s Awesome JavaScript repo: github.com/sorrycc/awesome-javascript.

Powerful UI frameworks made rich web applications much easier to build — at a cost. Instead of serving a complete HTML document, many sites now serve a blank page plus a large amount of JavaScript, and the user sees nothing until that code has downloaded and executed. Sites got slower. The solution is server-side rendering (SSR): the same code that would render the page in the browser renders it on the server, so a complete HTML document arrives before the JavaScript. Because SSR requires code that runs on both server and browser it can be tricky to implement — which is where some server frameworks help.

1.2.2 Server frameworks

Thanks to Node.js, JavaScript became one of the most popular languages for server development, particularly web servers. Since Node.js offers only low-level primitives for HTTP, almost every server uses a framework.

At its simplest, a server framework routes HTTP requests to handler functions that generate responses. Express is the popular minimal choice:

An Express serverJavaScript
import express from "express";

const app = express();            // #A
app.get("/ping", (req, res) => {   // #B
  res.send("OK");               // #C
});
#A Create an Express server
#B Define a handler for GET requests with the path “/ping”
#C Send a response with the message body “OK”

For more out-of-the-box functionality, Adonis ships authentication, internationalisation and an ORM for querying SQL databases. For content-centric sites such as blogs or online stores, a CMS framework like Keystone provides a full-featured foundation with minimal configuration.

Perhaps most interesting are the full-stack frameworks that blur the line between web server and UI: Next.js, Remix and Astro are built for high-performance React sites. They render on the server by default, split the site’s JavaScript into chunks delivered only to the pages that need them, and give frontend engineers a first-class workflow with a local dev server that uses Hot Module Replacement (HMR) to push changes into the browser without a refresh.

Note A curated list of the latest server frameworks plus other useful Node.js libraries lives in Sindre Sorhus’ Awesome Node.js repo: github.com/sindresorhus/awesome-nodejs. Using JavaScript as a server language is covered in Chapter 2.

1.2.3 App frameworks

JavaScript has expanded beyond the web into desktop and mobile applications. The big advantage of writing apps in JavaScript is “write once, run anywhere”: instead of a Swift app for iOS and macOS, a Kotlin app for Android and a C# app for Windows, you write one JavaScript application and deploy it to all of those platforms — and the web too.

At its simplest, an app framework is a thin native wrapper around an embedded web view, letting web developers reuse ordinary HTML and CSS. Electron does this for desktop apps and Ionic for mobile apps. Apps built this way have a reputation for low quality and ignoring platform design standards, but that needn’t be so: with the right component libraries and attention to detail, web-view apps look great everywhere — Slack, Notion and Figma are cited as polished examples.

React Native takes a different route: rather than rendering HTML and CSS in a web view, it renders UI components specific to the target platform. You still write JSX, but instead of HTML elements like <div> you use React Native constructs like <View>, which becomes UIView on iOS and android.view on Android. The result looks and feels like a separately written native app — Discord, Pinterest and Skype are named as examples.

JavaScript has been blessed with a passionate open-source community that maintains a wide range of frameworks. With the right framework and ninja skills, practically any project is within reach.

1.3 Using current best practices

Language mastery and a grasp of the ECMAScript standards matter, but they’re not the whole picture. To reach the big leagues you also need the habits that generations of developers have proven beneficial to quality code: type checking, linting/formatting and testing.

1.3.1 Type checking

One of JavaScript’s most notable quirks is its flexible type system: instead of throwing when operations cross incompatible types, the language bends over backward to make them happen, with counterintuitive results. For example, [] + {} produces the string "[object Object]", while [] + "" yields the empty string "". To be a ninja you don’t need to memorise every coercion rule; you need to know how to avoid them.

Unexpected types are one of the most common sources of errors — anyone who has seen the word undefined in the middle of a web page knows. Microsoft’s answer was TypeScript: a language that adds type annotations to JavaScript, with a compiler that checks the types satisfy the rules. Passing a string to a function expecting a number becomes a compile-time error rather than a runtime surprise:

Type checking catches a bad callTypeScript
const addOne = (x: number) => x + 1;  // #A
addOne("10");                              // #B
#A Defines a function that takes a number x and returns x + 1
#B Calls the function with a string, which will yield an error when the type checker runs

If this code were allowed to run, the result of addOne("10") would be "101".

Type annotations do more than prevent errors: they give tools a rich layer of information. In a full-featured editor such as VS Code you can see types as you work — which type does x have, what arguments does someFunc expect? TypeScript’s popularity has exploded; in the 2023 State of JavaScript survey, developers reported spending more time writing TypeScript than writing JavaScript directly. As adoption grows, so do the benefits, since more open-source libraries ship built-in type information.

1.3.2 Linting and formatting

In 2008 Douglas Crockford wrote the amusingly short JavaScript: The Good Parts. The language has gained many more good parts since — but the “bad parts”, the features and patterns that make code confusing, remain. A linter tells you when you step into that dark territory.

The most popular linter for JavaScript and TypeScript is ESLint, powerful and highly customisable. It can enforce as many rules as you like, from simple mistake-catchers like no-unreachable (code after a return or other short-circuit keyword) to library-specific advice like react/no-deprecated (calling one of React’s deprecated methods).

A simple rule that prevents common errors is no-shadow, which forbids “shadowing” — declaring a variable with the same name as one in the outer scope. This code doesn’t work as intended because of shadowing:

Shadowed variableJavaScript
let username = "Zork";

function logInAs(username) {   // #A
  username = username;      // #B
}

logInAs("Grue");
#A The no-shadow ESLint rule would flag this line, because a variable called username is declared in the surrounding scope
#B This line is a no-op, assigning the function argument to itself instead of modifying the username variable as intended

Linter rules can enforce style too: want every comment capitalised? Enable the capitalized-comments rule. Stylistic rules often come with auto-fix, so the linter simply changes the code rather than reporting an error.

A close cousin of the linter is the formatter, which makes code more readable by breaking long lines, applying consistent indentation and so on. The most popular formatter for JavaScript and TypeScript is Prettier, an enormous time-saver: instead of formatting by hand — or, worse, arguing with colleagues about formatting — Prettier handles it in the blink of an eye. Chapter 4 shows how to use ESLint and Prettier.

1.3.3 Testing

Type checking and linting catch many errors before they happen, but they are no substitute for running your code. A test framework lets you assert what will happen when code runs, in order to verify its behaviour. Ideally an application has at least two kinds of tests:

KindWhat it verifiesTypical tooling
Unit test Behaviour in isolation. Operations such as network requests are “mocked” to supply hard-coded input, known as fixtures. With no dependencies on other systems they run fast and rarely produce false positives from network errors; they usually run in a server runtime such as Node.js, with a simulated browser environment if needed. Vitest, Jest, Mocha; Node.js also has a built-in test runner
End-to-end test Behaviour as part of a system. User input is simulated, but dependencies such as databases and third-party APIs are real; for web apps these typically run in a real browser against the deployed site. They catch issues unit tests can’t, because unit tests can’t account for every failure mode that arises when parts of a system talk to each other. Playwright, Cypress

Testing is absolutely essential for real-world applications. To keep this book’s examples succinct, however, the authors verify behaviour with a terser approach: console.assert, which comes standard in all JavaScript environments. Its general form is:

The shape of console.assertJavaScript
console.assert(condition, message);

The first parameter is a condition you expect to be true. If it isn’t met, the error message is emitted to the console. For example:

Assertions in practiceJavaScript
const a = 1;
console.assert(a === 1, "a is not 1"); // No output
const b = 22;
console.assert(b === 2, "b is not 2"); // Emits "b is not 2"

These best-practice techniques, and others picked up along the way, greatly improve the development experience: they help you avoid common pitfalls and write code that is easier to maintain, scale and collaborate on.

1.4 Challenges facing JavaScript Ninjas

As JavaScript’s success has grown, new challenges have appeared. The chapter highlights three.

1.4.1 Performance

Engines keep getting more efficient, yet many JavaScript-heavy websites keep getting slower. Companies know a sluggish site hurts the bottom line: search engines penalise slow pages in their rankings, and potential customers who click a link lose patience after a few seconds. Turning a slow site into a fast one is a valuable — and measurable — service a ninja is well equipped to provide.

The most obvious cause of slow performance on the web is code bloat: an excessive amount of JavaScript sent to the browser. To understand it, consider the incentives developers face:

  • It’s usually easier to write code that runs in the browser than to write code that runs on the server.
  • It’s usually easier to implement a feature by adding an existing package than to write it from scratch.
  • It’s usually easier for a package author to combine a wide range of functionality in a single package than to write several modular packages covering different pieces of that functionality.

Taking the easy path at every step is a recipe for shipping unnecessary code. Even code that never runs must be downloaded and parsed, consuming bandwidth and CPU. Chapter 14 covers techniques for avoiding bloat: tree shaking to remove extraneous code, production flags to keep debugging code out of production, and lazy loading to defer code until it’s needed.

1.4.2 Collaboration at scale

On a complex site or app you are very likely looking at the work of multiple teams — a navigation header from one team, a product listing from a second, a shopping cart from a third. Dividing a product across teams means weighing tradeoffs carefully, and a ninja’s expertise can guide a company to the right architecture before it invests too much in the wrong one.

The simplest architecture is a single codebase deployed as a single unit. At scale the shared codebase causes conflicts, especially around dependencies: if one team wants a new version of React, the entire codebase must be updated to stay compatible — which may introduce bugs, and not every team will be delighted to pause feature work while someone updates their corner of the code.

Large projects therefore divide the codebase into separate units that each team can update independently, dependency changes included. But that raises its own question: how do multiple teams independently deploy code used on different parts of the same web page? Chapter 14 introduces module federation, which allows different parts of pages to be deployed independently (see also Micro Frontends in Action by Michael Geers). Chapter 18 covers codemods, tools that automate code migrations and greatly reduce the friction of coordinating changes across teams.

1.4.3 Dependency management

A theme runs through these challenges: dependencies complicate everything. Beyond what’s already been touched on, there are more ways for dependencies to ruin your day:

  • You update a dependency to pull in a bugfix, only to hit breaking changes in its behaviour, because package authors routinely ignore semantic versioning rules.
  • You install one version of a package and end up with an indirect dependency on another, so both versions try to run in your application and conflict.
  • You want a package published as an ES module, only to hit errors in an environment that expects CommonJS — or vice versa.
  • Every JavaScript developer’s worst nightmare: a supply chain attack, where a third-party package becomes a vector for malicious code that runs on your development machine or wherever you deploy.

Chapter 3 covers some of these issues while introducing npm, and Chapter 14 compares ES modules with CommonJS. One nice thing about JavaScript: before adding third-party code you can read it yourself. As a ninja you’ll be equipped to anticipate problems a dependency might bring — and to estimate the effort of implementing the functionality yourself.

1.5 Summary

  1. JavaScript is everywhere. Beyond being the language of the web, it can build applications for every major computing platform.
  2. The language has evolved dramatically and keeps improving every year; depending on where you expect your code to run, you may need to transpile to use the latest features.
  3. Most modern JavaScript projects use an open-source framework. Choosing the right one gives a critical edge.
  4. Best practices — type checking, linting and testing — are key to robust, reliable code.
  5. The biggest challenges facing JavaScript developers are performance, collaboration at scale and dependency management.
  6. This book focuses on the core mechanics of the language. Mastering those fundamentals helps you architect, write and maintain robust JavaScript applications.
