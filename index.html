What the chapter covers

JavaScript started life in 1995 as a ten-day project to add a scripting language to Netscape’s browser. Today it is one of the most widely used languages in the world: it runs websites, servers, mobile and desktop apps, game consoles, IoT devices — and, increasingly, your car. The chapter opens by asking how a single language made the leap from the browser to the wider world of computing. The answer, in one word: evolution.

For years JavaScript carried a reputation for being slow and quirky, with none of the comforts other languages offered — rich IDE integration, static analysis, debugging tools, a package distribution system. Developers tolerated it because it was the only language browsers ran, but few loved it. Three things changed that:

  • Competition between browser vendors produced dramatically faster engines.
  • Cooperation between them produced the ECMAScript standards process for new language features.
  • The Node.js runtime took JavaScript outside the browser and brought with it an entire package ecosystem and a toolchain written in JavaScript itself.

The chapter in three points:

  • What makes JavaScript special
  • How JavaScript evolves over time
  • Three best practices in JavaScript development

Thanks to that evolution, JavaScript is both enormously versatile and — for most purposes — reasonably performant. Developer experience improved too: the IDE integration and static analysis people once only dreamed about now arrive via TypeScript. TypeScript has become so popular that it is nearly synonymous with JavaScript development, and the authors admit they considered calling this book Secrets of the TypeScript Ninja. But TypeScript is just a tool for developing JavaScript, so the book integrates it in that spirit.

The book’s plan is to build understanding from the ground up — fundamentals first, then the “secret” techniques that separate the JavaScript Ninja from the ordinary developer.

1.1 Understanding the JavaScript language

A common trap: assuming that knowing C# or Java means you already understand JavaScript. Compared with other mainstream languages, JavaScript is far more functionally oriented, and several of its concepts differ fundamentally.

DifferenceWhat it meansWhere it’s covered
Functions are first-class objects Functions coexist with, and can be treated like, any other object: assigned to variables, passed as arguments, even created by other functions. Chapter 5
Prototype-based object orientation Unlike class-based languages (C#, Java, Ruby), JavaScript uses prototypes. It has a class keyword today, but under the hood those classes are defined in terms of prototypes. Chapter 9
Single-threaded Code runs on a single thread; asynchronous work relies on callbacks and promises, with workers available to move work off the main thread. Chapters 3, 8 and 14

JavaScript is really a set of close relationships: objects and prototypes, and functions and closures. Understanding those relationships is the foundation for any kind of application — browser, server or app.

On top of the fundamentals, the book covers language features that make code more elegant and efficient:

  • Promises — better control over asynchronous code.
  • Advanced array methods — much more elegant array handling.
  • Maps and sets — dictionary collections, and collections of unique items.
  • Regular expressions — simplify what would otherwise be complicated code.
  • Modules — break code into smaller, self-contained pieces that keep projects manageable.

1.1.1 JavaScript runtimes and engines

JavaScript’s popularity has taken it to browsers, servers, apps, consoles and devices, which means many runtimes — environments that execute JavaScript. Node.js is the best-known non-browser runtime, facing growing competition from Deno and Bun.

Under the hood every runtime uses an engine to convert JavaScript into machine instructions for the CPU. Modern engines use just-in-time (JIT) compilation to optimise code as it runs, and are continuously improved for speed and for new ECMAScript features. Two notable engines: V8 (Chrome and Node.js) and JavaScriptCore (Safari and Bun).

A runtime also supplies API bindings, which let your code interact with its host environment. In the browser you might fetch data over the network, listen for user events and update the DOM; in Node.js you might listen on a TCP socket, write to disk and spawn subprocesses.

Some code is deliberately cross-runtime — Lodash, for example, is used in browsers, servers and apps alike — while other code targets one runtime. Either way, code crosses over: Node.js can simulate a browser with jsdom (useful for testing or pre-rendering HTML), and browsers can simulate Node.js with WebContainers (useful for secure sandboxes and zero-install dev environments).

Note Most of the techniques in this book work in any modern JavaScript runtime, browser or standalone. The book flags exceptions as it goes. Node.js is the focus of Chapter 3 and browsers of Chapter 4 — and even browser-only developers will want Node.js for the development environment and build pipeline.

1.1.2 How does JavaScript get new features?

Shortly after Netscape introduced the language in 1995, a committee formed to standardise it. Because of Sun Microsystems’ trademark on the word “Java” — which Netscape was using under licence — that committee is now the ECMAScript Committee. In practice ECMAScript and JavaScript are synonyms: ECMAScript appears in official specifications, JavaScript is the popular name everywhere else.

For years the standard changed little, concentrating on consistent behaviour across implementations. That changed in 2015, when ES6 (later renamed ES2015) brought arrow functions, maps, promises, modules and much more. Since then a new standard has landed every year: ES2016, ES2017, and so on.

That steady drip of features is exciting, but it means you must know which features the runtimes you target actually support — especially on the web, where the runtime is the user’s possibly-ancient browser. Chapter 14 covers strategies for targeting a wide range of browsers, and the ECMAScript compatibility table shows which runtimes support a given feature.

1.1.3 Transpilers and polyfills give us access to tomorrow’s JavaScript today

You can use the newest features without waiting for universal support, in two complementary ways:

  • Transpiler (“transformation + compiler”) — rewrites cutting-edge code into a functionally equivalent form limited to older ECMAScript features. The idea was pioneered by Babel, and the TypeScript compiler also transpiles syntax down to a target ECMAScript version.
  • Polyfill — code that defines a feature in runtimes where it isn’t natively provided. Want promises (ES6) but must support Internet Explorer 11 (stuck on ES5)? A polyfill can define a global Promise with the same behaviour as the ES6 API.

Polyfills are often used together with transpilation — Babel can inject the needed polyfills while it transpiles; TypeScript doesn’t, which is one reason TypeScript and Babel are frequently paired.

Some features simply cannot be implemented efficiently in older runtimes. Regex lookbehind assertions, added in ES2018, are the example: in a runtime without that feature the regex fails, transpiled or not. So know which runtimes you target and what they support — and, better still, automate tests for those runtimes.

1.2 Navigating the world of frameworks

JavaScript’s open-source ecosystem puts millions of libraries at your fingertips, and choosing the right ones is a critical skill. For most projects the first question is: which framework?

A framework is a library that powers the core functionality of your application. A web app uses its framework to render HTML; a server app uses its framework to parse HTTP requests and send responses. You could build the same functionality yourself, but a well-chosen framework saves an enormous amount of time — nearly all modern JavaScript applications are built on one.

1.2.1 Web UI frameworks

Early JavaScript added a dash of interactivity to otherwise static sites: the browser downloaded and rendered a complete HTML document, then ran a script for enhancements such as form validation. The dominant frameworks — jQuery above all — were thin wrappers around browser APIs, smoothing over cross-browser differences. Complex web apps were awkward, because you bounced back and forth between HTML and JavaScript.

In the 2010s a new generation of frameworks let developers write HTML inside JavaScript. One of them, React, soon ruled the web, introducing JSX — a way to write JavaScript and HTML together that feels natural:

React component using JSXJSX
import React, {useState} from "react";

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <div>The count is {count}.</div>
      <button
        onClick={() => {
          setCount(count + 1);
        }}
      >
        Increment count
      </button>
    </div>
  );
}

Under the hood React uses a virtual DOM: it builds a tree describing what the page’s HTML should look like, compares that tree against the existing HTML, and then updates the page so the two match. That saves developers from touching the DOM directly. React has no shortage of challengers — Angular, Vue and Svelte among them — and many borrow JSX or a similar templating language, adding their own spin on React’s paradigm rather than overturning it. A key factor when choosing is the ecosystem: a newer framework may be more elegant and efficient, but React gives access to thousands of ready-made component libraries.

Note The JavaScript library world moves fast. One excellent resource for keeping up with browser-based JavaScript is Chen Cheng’s Awesome JavaScript repo: github.com/sorrycc/awesome-javascript.

Powerful UI frameworks made rich web applications much easier to build — at a cost. Instead of serving a complete HTML document, many sites now serve a blank page plus a large amount of JavaScript, and the user sees nothing until that code has downloaded and executed. Sites got slower. The solution is server-side rendering (SSR): the same code that would render the page in the browser renders it on the server, so a complete HTML document arrives before the JavaScript. Because SSR requires code that runs on both server and browser it can be tricky to implement — which is where some server frameworks help.

1.2.2 Server frameworks

Thanks to Node.js, JavaScript became one of the most popular languages for server development, particularly web servers. Since Node.js offers only low-level primitives for HTTP, almost every server uses a framework.

At its simplest, a server framework routes HTTP requests to handler functions that generate responses. Express is the popular minimal choice:

An Express serverJavaScript
import express from "express";

const app = express();            #A
app.get("/ping", (req, res) => {   #B
  res.send("OK");               #C
});
#A Create an Express server
#B Define a handler for GET requests with the path “/ping”
#C Send a response with the message body “OK”

For more out-of-the-box functionality, Adonis ships authentication, internationalisation and an ORM for querying SQL databases. For content-centric sites such as blogs or online stores, a CMS framework like Keystone provides a full-featured foundation with minimal configuration.

Perhaps most interesting are the full-stack frameworks that blur the line between web server and UI: Next.js, Remix and Astro are built for high-performance React sites. They render on the server by default, split the site’s JavaScript into chunks delivered only to the pages that need them, and give frontend engineers a first-class workflow with a local dev server that uses Hot Module Replacement (HMR) to push changes into the browser without a refresh.

Note A curated list of the latest server frameworks plus other useful Node.js libraries lives in Sindre Sorhus’ Awesome Node.js repo: github.com/sindresorhus/awesome-nodejs. Using JavaScript as a server language is covered in Chapter 2.

1.2.3 App frameworks

JavaScript has expanded beyond the web into desktop and mobile applications. The big advantage of writing apps in JavaScript is “write once, run anywhere”: instead of a Swift app for iOS and macOS, a Kotlin app for Android and a C# app for Windows, you write one JavaScript application and deploy it to all of those platforms — and the web too.

At its simplest, an app framework is a thin native wrapper around an embedded web view, letting web developers reuse ordinary HTML and CSS. Electron does this for desktop apps and Ionic for mobile apps. Apps built this way have a reputation for low quality and ignoring platform design standards, but that needn’t be so: with the right component libraries and attention to detail, web-view apps look great everywhere — Slack, Notion and Figma are cited as polished examples.

React Native takes a different route: rather than rendering HTML and CSS in a web view, it renders UI components specific to the target platform. You still write JSX, but instead of HTML elements like <div> you use React Native constructs like <View>, which becomes UIView on iOS and android.view on Android. The result looks and feels like a separately written native app — Discord, Pinterest and Skype are named as examples.

JavaScript has been blessed with a passionate open-source community that maintains a wide range of frameworks. With the right framework and ninja skills, practically any project is within reach.

1.3 Using current best practices

Language mastery and a grasp of the ECMAScript standards matter, but they’re not the whole picture. To reach the big leagues you also need the habits that generations of developers have proven beneficial to quality code: type checking, linting/formatting and testing.

1.3.1 Type checking

One of JavaScript’s most notable quirks is its flexible type system: instead of throwing when operations cross incompatible types, the language bends over backward to make them happen, with counterintuitive results. For example, [] + {} produces the string "[object Object]", while [] + "" yields the empty string "". To be a ninja you don’t need to memorise every coercion rule; you need to know how to avoid them.

Unexpected types are one of the most common sources of errors — anyone who has seen the word undefined in the middle of a web page knows. Microsoft’s answer was TypeScript: a language that adds type annotations to JavaScript, with a compiler that checks the types satisfy the rules. Passing a string to a function expecting a number becomes a compile-time error rather than a runtime surprise:

Type checking catches a bad callTypeScript
const addOne = (x: number) => x + 1;  #A
addOne("10");                              #B
#A Defines a function that takes a number x and returns x + 1
#B Calls the function with a string, which will yield an error when the type checker runs

If this code were allowed to run, the result of addOne("10") would be "101".

Type annotations do more than prevent errors: they give tools a rich layer of information. In a full-featured editor such as VS Code you can see types as you work — which type does x have, what arguments does someFunc expect? TypeScript’s popularity has exploded; in the 2023 State of JavaScript survey, developers reported spending more time writing TypeScript than writing JavaScript directly. As adoption grows, so do the benefits, since more open-source libraries ship built-in type information.

1.3.2 Linting and formatting

In 2008 Douglas Crockford wrote the amusingly short JavaScript: The Good Parts. The language has gained many more good parts since — but the “bad parts”, the features and patterns that make code confusing, remain. A linter tells you when you step into that dark territory.

The most popular linter for JavaScript and TypeScript is ESLint, powerful and highly customisable. It can enforce as many rules as you like, from simple mistake-catchers like no-unreachable (code after a return or other short-circuit keyword) to library-specific advice like react/no-deprecated (calling one of React’s deprecated methods).

A simple rule that prevents common errors is no-shadow, which forbids “shadowing” — declaring a variable with the same name as one in the outer scope. This code doesn’t work as intended because of shadowing:

Shadowed variableJavaScript
let username = "Zork";

function logInAs(username) {   #A
  username = username;      #B
}

logInAs("Grue");
#A The no-shadow ESLint rule would flag this line, because a variable called username is declared in the surrounding scope
#B This line is a no-op, assigning the function argument to itself instead of modifying the username variable as intended

Linter rules can enforce style too: want every comment capitalised? Enable the capitalized-comments rule. Stylistic rules often come with auto-fix, so the linter simply changes the code rather than reporting an error.

A close cousin of the linter is the formatter, which makes code more readable by breaking long lines, applying consistent indentation and so on. The most popular formatter for JavaScript and TypeScript is Prettier, an enormous time-saver: instead of formatting by hand — or, worse, arguing with colleagues about formatting — Prettier handles it in the blink of an eye. Chapter 4 shows how to use ESLint and Prettier.

1.3.3 Testing

Type checking and linting catch many errors before they happen, but they are no substitute for running your code. A test framework lets you assert what will happen when code runs, in order to verify its behaviour. Ideally an application has at least two kinds of tests:

KindWhat it verifiesTypical tooling
Unit test Behaviour in isolation. Operations such as network requests are “mocked” to supply hard-coded input, known as fixtures. With no dependencies on other systems they run fast and rarely produce false positives from network errors; they usually run in a server runtime such as Node.js, with a simulated browser environment if needed. Vitest, Jest, Mocha; Node.js also has a built-in test runner
End-to-end test Behaviour as part of a system. User input is simulated, but dependencies such as databases and third-party APIs are real; for web apps these typically run in a real browser against the deployed site. They catch issues unit tests can’t, because unit tests can’t account for every failure mode that arises when parts of a system talk to each other. Playwright, Cypress

Testing is absolutely essential for real-world applications. To keep this book’s examples succinct, however, the authors verify behaviour with a terser approach: console.assert, which comes standard in all JavaScript environments. Its general form is:

The shape of console.assertJavaScript
console.assert(condition, message);

The first parameter is a condition you expect to be true. If it isn’t met, the error message is emitted to the console. For example:

Assertions in practiceJavaScript
const a = 1;
console.assert(a === 1, "a is not 1"); // No output
const b = 22;
console.assert(b === 2, "b is not 2"); // Emits "b is not 2"

These best-practice techniques, and others picked up along the way, greatly improve the development experience: they help you avoid common pitfalls and write code that is easier to maintain, scale and collaborate on.

1.4 Challenges facing JavaScript Ninjas

As JavaScript’s success has grown, new challenges have appeared. The chapter highlights three.

1.4.1 Performance

Engines keep getting more efficient, yet many JavaScript-heavy websites keep getting slower. Companies know a sluggish site hurts the bottom line: search engines penalise slow pages in their rankings, and potential customers who click a link lose patience after a few seconds. Turning a slow site into a fast one is a valuable — and measurable — service a ninja is well equipped to provide.

The most obvious cause of slow performance on the web is code bloat: an excessive amount of JavaScript sent to the browser. To understand it, consider the incentives developers face:

  • It’s usually easier to write code that runs in the browser than to write code that runs on the server.
  • It’s usually easier to implement a feature by adding an existing package than to write it from scratch.
  • It’s usually easier for a package author to combine a wide range of functionality in a single package than to write several modular packages covering different pieces of that functionality.

Taking the easy path at every step is a recipe for shipping unnecessary code. Even code that never runs must be downloaded and parsed, consuming bandwidth and CPU. Chapter 14 covers techniques for avoiding bloat: tree shaking to remove extraneous code, production flags to keep debugging code out of production, and lazy loading to defer code until it’s needed.

1.4.2 Collaboration at scale

On a complex site or app you are very likely looking at the work of multiple teams — a navigation header from one team, a product listing from a second, a shopping cart from a third. Dividing a product across teams means weighing tradeoffs carefully, and a ninja’s expertise can guide a company to the right architecture before it invests too much in the wrong one.

The simplest architecture is a single codebase deployed as a single unit. At scale the shared codebase causes conflicts, especially around dependencies: if one team wants a new version of React, the entire codebase must be updated to stay compatible — which may introduce bugs, and not every team will be delighted to pause feature work while someone updates their corner of the code.

Large projects therefore divide the codebase into separate units that each team can update independently, dependency changes included. But that raises its own question: how do multiple teams independently deploy code used on different parts of the same web page? Chapter 14 introduces module federation, which allows different parts of pages to be deployed independently (see also Micro Frontends in Action by Michael Geers). Chapter 18 covers codemods, tools that automate code migrations and greatly reduce the friction of coordinating changes across teams.

1.4.3 Dependency management

A theme runs through these challenges: dependencies complicate everything. Beyond what’s already been touched on, there are more ways for dependencies to ruin your day:

  • You update a dependency to pull in a bugfix, only to hit breaking changes in its behaviour, because package authors routinely ignore semantic versioning rules.
  • You install one version of a package and end up with an indirect dependency on another, so both versions try to run in your application and conflict.
  • You want a package published as an ES module, only to hit errors in an environment that expects CommonJS — or vice versa.
  • Every JavaScript developer’s worst nightmare: a supply chain attack, where a third-party package becomes a vector for malicious code that runs on your development machine or wherever you deploy.

Chapter 3 covers some of these issues while introducing npm, and Chapter 14 compares ES modules with CommonJS. One nice thing about JavaScript: before adding third-party code you can read it yourself. As a ninja you’ll be equipped to anticipate problems a dependency might bring — and to estimate the effort of implementing the functionality yourself.

1.5 Summary

  1. JavaScript is everywhere. Beyond being the language of the web, it can build applications for every major computing platform.
  2. The language has evolved dramatically and keeps improving every year; depending on where you expect your code to run, you may need to transpile to use the latest features.
  3. Most modern JavaScript projects use an open-source framework. Choosing the right one gives a critical edge.
  4. Best practices — type checking, linting and testing — are key to robust, reliable code.
  5. The biggest challenges facing JavaScript developers are performance, collaboration at scale and dependency management.
  6. This book focuses on the core mechanics of the language. Mastering those fundamentals helps you architect, write and maintain robust JavaScript applications.

Using modern JavaScript tools

This chapter covers

  • Three tools that have taken the JavaScript world by storm
  • Why most JavaScript code is now written in TypeScript
  • How productive teams resolve arguments about code style

In the early days of JavaScript engineers had a common refrain: “It’s not a real language.” The idea was that JavaScript was a toy, decent for simple scripts but ill-suited to “serious” programming.

That attitude has largely disappeared. The language itself has evolved, certainly — a steady stream of ECMAScript iterations adding features. But the more significant change is how JavaScript is written. When engineers said it wasn’t a real language, they meant it lacked the guardrails Java and C# provide: reference an undefined variable, call a function with the wrong number of arguments, do arithmetic on a string, and those languages complain at compile time — or better, in the IDE. In JavaScript you wouldn’t know until the code runs (if then).

Three tools transformed that experience:

  • TypeScript made compile-time type checking a reality, and powerful IDE integration with it.
  • ESLint made it easy to enforce whatever rules you want, from the common-sensical to the esoteric.
  • Prettier ended a million arguments about what JavaScript code should look like.

This chapter is more hands-on than the rest of the book, because the only way to understand these tools is to start using them. Once they’re set up, you’re equipped to work with the code examples that follow.

Running tools with Node.js

One key ingredient in JavaScript’s rise has been the ability to write JavaScript tools in JavaScript. That trend started with Node.js, which has become the standard runtime for JavaScript tooling. This chapter assumes Node.js is set up so that you can run the node, npm and npx commands; for step-by-step installation and version management, see Appendix A.

2.1 Type checking with TypeScript

Mismatched types are one of the most common sources of JavaScript errors, and an easy mistake to make. Say you misremember the order of arguments to setTimeout:

Incorrect argument orderJavaScript
// Incorrect code! The time should come after the callback.
setTimeout(200, () => {
  console.log("This will never run.");
});

Run this in a browser and something strange happens: nothing. No error is thrown, no message appears in the console. Many browser APIs behave that way, which makes bugs from a failed timeout hard to track down. Node.js is, helpfully, stricter: the invalid setTimeout triggers a runtime error with an informative message. But why wait until runtime to discover an error that could have been predicted just by looking at the code?

Many attempts have been made to solve this. Most involved generating JavaScript from a completely different language — Google’s GWT compiles Java into a browser-friendly JavaScript application, for instance. TypeScript takes another approach: rather than being a different language, it is a superset of JavaScript with types that can be verified at compile time.

Because it’s a superset, the setTimeout code above is also valid TypeScript, yet the type checker can still recognise the error. You can see it for yourself in the TypeScript Playground.

Types of typed languages

When developers complain that JavaScript has no proper types, two separate concepts are in play:

  • JavaScript is dynamically typed: types are enforced only at runtime. In a statically typed language they are enforced at compile time. TypeScript is statically typed, because its type checker runs before your code does.
  • JavaScript has implicit type coercion: 1 + "2" produces the string "12", because anything added to a string is converted. TypeScript keeps every runtime behaviour of JavaScript, so coercion still happens — but being weakly typed is less likely to cause errors, because the type checker can predict coercion: it knows 1 + "2" is a string, and errors if that value is used where a string isn’t expected.

2.1.2 Type annotations and declarations

The code below defines and tests a small utility that pluralises strings. Save it as pluralize.ts:

Listing 2.3 — A TypeScript file with untyped function argumentsTypeScript
const pluralize = (str, count) => (count === 1 ? str : `${str}s`);

console.assert(
  pluralize("egg", 1) === "egg",
  "pluralize returns the original string when count is 1",
);
console.assert(
  pluralize("egg", 2) === "eggs",
  "pluralize appends 's' when count is 2",
);

The code is perfectly valid JavaScript. Run it through the compiler, though, and you get an error (though — as before — the error doesn’t block compilation): 

$ npx tsc --noEmit
pluralize.ts:1:20 - error TS7006: Parameter 'str' implicitly has an 'any' type.

1 const pluralize = (str, count) => (count === 1 ? str : `${str}s`);
                     ~~~

pluralize.ts:1:25 - error TS7006: Parameter 'count' implicitly has an 'any' type.

1 const pluralize = (str, count) => (count === 1 ? str : `${str}s`);
                            ~~~~~

Now the any type. The type checker infers every variable’s type from the context in which it’s declared: in let x = 5 it infers x is a number from the initial value; in addEventListener("keydown", (event) => console.log(event.key)) it infers event is a KeyboardEvent from where the function was defined. It looks at nothing outside that initial declaration, so when it sees (str, count) in a function assigned to an untyped variable it has nothing to go on, throws up its arms, and falls back on any.

any is unlike any other TypeScript type: it effectively disables type checking for that variable. It’s an escape hatch that can be valuable while migrating JavaScript to TypeScript, but should otherwise be avoided. So the compiler emits an error whenever a value implicitly receives any — controlled by noImplicitAny, which the strict flag flips on.

Note TypeScript’s strict mode only prohibits implicit any. To stop developers using any at all, typescript-eslint offers the no-explicit-any rule.

The fix is to tell the type checker what argument types the function accepts. The most direct way is a type annotation on each argument:

Annotating the parametersTypeScript
const pluralize = (str: string, count: number) =>
  count === 1 ? str : `${str}s`;

With those annotations the checker can do its job, raising an error for anything in the body or in calls that isn’t compatible with those types. They also give it enough information to infer that pluralize always returns a string.

Alternatively, annotate the function itself — one annotation meaning “pluralize takes a string and a number and returns a string”:

Annotating the functionTypeScript
const pluralize: (str: string, count: number) => string =
  (str, count) =>
    count === 1 ? str : `${str}s`;

Annotating the function looks a little ridiculous, since it duplicates information already in the declaration, but it’s worth knowing: the compiler is equally happy whether it infers parameter types from the function type or vice versa. It also demonstrates that types can get complicated — which is why we don’t have to put them all inline. We can use type declarations.

Listing 2.4 — A function parameter with a separate type declarationTypeScript
interface StarshipOptions {            #A
  captain: "Kirk" | "Picard" | "Janeway";   #B
  warpFactor: number;
  engage?: boolean;                                   #C
};

const startStarship = (options: StarshipOptions) => {
  const { captain, warpFactor, engage } = options;
  if (!engage) {
    return "Awaiting orders from Starfleet.";
  }
  return `Captain ${captain} says: Set warp ${warpFactor}. Engage!`;
};
#A The interface keyword indicates we’re declaring a type. Here it’s an object type, so the structure mimics object-literal syntax. By convention, type names are capitalised.
#B The | character defines a union type: here, three literal values joined into “one of these three values”.
#C The ? after a key makes the value optional — it can be undefined or omitted entirely.

The type of options could have been written inline, but extracting and naming complex types makes for more readable code. Declared types are also reusable: types follow the same scoping rules as function declarations, so they can be referenced anywhere in the module and shared with import/export. And you can derive new types from them — which is what the next section does.

Types vs. interfaces

Object types can be defined two ways in TypeScript: with the interface keyword, as in Listing 2.4, or with the type keyword. The official handbook advises: “For the most part, you can choose based on personal preference, and TypeScript will tell you if it needs something to be the other kind of declaration. If you would like a heuristic, use interface until you need to use features from type.” The book’s code follows that recommendation.

You can enforce the interface keyword for object types with typescript-eslint’s prefer-interface rule.

2.1.3 Type narrowing and predicates

Working with TypeScript types you’ll constantly see the union operator, |. Consider this example:

Listing 2.5 — Using the type union operatorTypeScript
interface Mage {
  magic: number;
}
interface Thief {
  dexterity: number;
}
interface MageThief extends Mage, Thief {}    #A

const rerollAttributes = (character: Mage | Thief) => {   #B
  if ("magic" in character) {                           #C
    character.magic = Math.ceil(Math.random() * 20);
  }
  if ("dexterity" in character) {
    character.dexterity = Math.ceil(Math.random() * 20);
  }
};
#A The extends operator creates a new interface that inherits the properties of Mage and Thief.
#B The | character creates a union of types — character can be a Mage or a Thief, or any superset of those types.
#C The in keyword performs a runtime check: does this property exist on this object?

This demonstrates type narrowing. Without the in checks before assigning values, the type checker would complain: 

error TS2339: Property 'magic' does not exist on type 'Mage | Thief | MageThief'.
  Property 'magic' does not exist on type 'Thief'.

Because we check that character has magic before assigning it, the checker knows character can’t be a Thief — it can only be a Mage, or more precisely any object with a mage’s properties. (A MageThief qualifies; so does an undeclared object like {magic: 15, luck: 20}.)

This kind of check is sometimes called duck typing, from “if it walks like a duck, and it talks like a duck…” Developers from more strongly typed languages find that strange, and their instinct is to write: 

// This won’t work!
if (character instanceof Mage)

The problem is that it conflates types with JavaScript code — types don’t exist at runtime! Fortunately the checker catches the mistake: 

error TS2693: 'Mage' only refers to a type, but is being used as a value here.

(instanceof is useful when you want to know whether an object is an instance of a class; Chapter 9 covers classes.) The compiled JavaScript contains the duck-type checks but no remnants of the types themselves:

Compiled output — types erasedJavaScript
"use strict";
const rerollAttributes = (character) => {
  if ("magic" in character) {
    character.magic = Math.ceil(Math.random() * 20);
  }
  if ("dexterity" in character) {
    character.dexterity = Math.ceil(Math.random() * 20);
  }
};

There are many ways to narrow types in TypeScript. Listing 2.6 shows a few of the most common checks:

Listing 2.6 — An assortment of type narrowing operationsTypeScript
const getValueWithType = (value?: string | string[] | 23) => {   #A
  if (value === 23) {                                     #B
    return `number: ${value}`;
  }
  if (typeof value === "string") {                      #C
    return `string: ${value}`;
  }
  if (Array.isArray(value)) {                              #D
    return `array: ${value.join(", ")}`;
  }
  value satisfies undefined;                               // #E
  return "undefined";
};
#A The ? makes value an optional parameter, meaning it can have the value undefined.
#B Checking for equality with a primitive value narrows the type to that exact value.
#C Using typeof narrows the type to that primitive type.
#D Using Array.isArray narrows the type to an array. Because the only array type in the parameter annotation is string[], it’s narrowed to an array of strings.
#E The satisfies keyword makes a claim about a type. If value could have any type other than undefined on this line, the type checker would raise an error.

The checker is clever about which possible types a value can have at any point in your code — but it has a couple of big limitations. One is that it struggles to notice when mutable structures such as objects and arrays are modified:

Widened mutable arrayTypeScript
const mixedArray = ["str", 123];        // type: (string | number)[]
const firstItem = mixedArray[0];      // type: string | number

If you never plan to modify the structure, add as const after the literal (see Matt Pocock’s article on as const):

With as constTypeScript
const mixedArray = ["str", 123] as const;    // type: ["str", 123]
const firstItem = mixedArray[0];                  // type: "str"

Another limitation you’ll often hit: the checker can’t always narrow the way you’d expect based on a function call. For example:

Which calls narrow?TypeScript
const stringOrNumber = ["str", 123][0];   // type: string | number
const isString = (x: unknown) => typeof x === "string";
const isShortString = (x: unknown) => {
  return typeof x === "string" && x.length <= 3;
}

if (typeof stringOrNumber === "string") {
  stringOrNumber satisfies string;              // assertion passes
}
if (isString(stringOrNumber)) {
  stringOrNumber satisfies string;              // assertion passes
}
if (isShortString(stringOrNumber)) {
  stringOrNumber satisfies string;              // assertion fails!
}

With isString, TypeScript correctly infers that if the function returns true then x must be a string. So why not with isShortString? It’s a limitation in how TypeScript stores function type information: it only draws the inference “if this returns true, x must be a string” if it can conversely draw “if this returns false, x must not be a string.” It can’t do that for isShortString, so it makes no inference at all.

One workaround is a type predicate — an annotation on a boolean function that forces the checker to make an inference. But it also forces the converse inference, which can introduce bugs:

Listing 2.7 — Using a type predicate, with a surprising resultTypeScript
const shortOrLongString = ["str", "long string"][0];   // type: string
const isShortString = (x: unknown): x is string => {      #A
  return typeof x === "string" && x.length <= 3;
};

if (isShortString(shortOrLongString)) {
  shortOrLongString satisfies string;                      #B
} else {
  shortOrLongString satisfies never;                       #C
}
#A This predicate tells the type checker that if the function returns true, then its argument is a string.
#B The satisfies keyword confirms the type has been narrowed to string.
#C The satisfies keyword confirms the type has been narrowed to never.

The x is string predicate tells the checker that x is a string when isShortString returns true — reasonable enough — except that it also implicitly tells the checker x is not a string when it returns false. Since we passed a string, TypeScript infers the result can’t be false, so in that branch it infers shortOrLongString has the special type never.

Inlining the function logic would avoid the problem, but in principle you shouldn’t have to bend runtime code to satisfy the type checker. There’s an escape hatch: the as keyword, which essentially says “I know something about this variable’s type that you don’t.”

Asserting the typeTypeScript
if (isShortString(stringOrNumber)) {
  const shortString = stringOrNumber as string; // type: string
  // ...
}

Just use as with caution: the type checker is only as accurate as the type information you give it.

2.1.4 Running TypeScript without compilation

As TypeScript took the world by storm, one of the biggest complaints has been speed: large projects can take several minutes to compile, a painful speed bump in an otherwise smooth workflow.

Fortunately, running TypeScript directly is now possible. Node.js 22.6.0 and newer can run most TypeScript code directly given a flag, --experimental-strip-types: 

$ echo "console.log('Hello, TypeScript!');" > hello.ts
$ node --experimental-strip-types hello.ts
Hello TypeScript!

The flag won’t work for code using TypeScript’s enum or namespace features — controversial exceptions to the rule that TypeScript is JavaScript with type annotations. None of the book’s code uses enum or namespace. TypeScript 5.8 added a configuration option, erasableSyntaxOnly, that ensures all your code is compatible with type stripping.

By the time you read this, the latest Node.js may well run TypeScript without any flags; both Deno and Bun already can.

There’s one big caveat: the runtime is only stripping type information, not running the type checks. Type checking remains a separate process (except in Deno, where checking while running is on by default). With that in mind, running code directly without waiting for a type check or compilation is a huge boon for tasks like running scripts and testing.

Compilation still has its place. Browsers don’t look likely to support TypeScript any time soon, and even if they did you’d still strip types as part of minification. And to support older runtimes, TypeScript must be transpiled to a specific ECMAScript version (minification and transpilation are covered in Chapter 13).

For most developers the biggest benefit is real-time feedback in modern editors like VS Code, where type errors appear as you write and type information (“What arguments does the function I’m calling expect?”) is a command away. Full project-wide type checks are valuable too, but they can run occasionally in continuous integration (CI) so they don’t get in your way while working.

That wraps up the TypeScript overview; Chapter 5 discusses more of its benefits, and the book keeps using it in examples. For a comprehensive look at the language, see Essential TypeScript 5 by Adam Freeman. Next: another tool that transformed JavaScript development — ESLint.

2.2 Enforcing code rules with ESLint

How do you make sure your code works? Ideally you test it — with a unit testing library like Vitest to simulate interactions. But writing tests takes time (though LLMs can help). And even at 100% coverage — every line runs when tests run — there’s still a chance some unanticipated set of conditions produces unintended behaviour.

That’s why you also want tools that perform static analysis: checking code for possible mistakes without running it. It’s a low-effort way to catch bugs before they happen. TypeScript is the static analysis tool for type misuse; ESLint is the static analysis tool for everything else.

2.2.1 Setting up ESLint in a TypeScript project

Let’s set up a project with both TypeScript and ESLint. To lint TypeScript code we need both packages plus one more, typescript-eslint. (These instructions are accurate as of typescript-eslint version 8; see typescript-eslint.io/getting-started for the latest.)

As before, start with an empty package.json so npm can track dependencies:

$ echo "{}" > package.json

Install ESLint, TypeScript and typescript-eslint. Note that ESLint requires two packages: eslint and @eslint/js. 

$ npm install --save-dev eslint @eslint/js typescript typescript-eslint

Then generate the default TypeScript configuration:

$ npx tsc --init

Now configure ESLint by creating eslint.config.mjs:

Listing 2.8 — A starter ESLint configuration for a TypeScript projectES module
// @ts-check                                   #A
import eslint from "@eslint/js";
import { defineConfig } from "eslint/config";
import tseslint from "typescript-eslint";

export default defineConfig([
  {                                          #B
    extends: [eslint.configs.recommended],   #B
  },                                         #B
  {
    files: ["**/*.{ts,mts}"],                #C
    extends: [                               #C
      tseslint.configs.strictTypeChecked     #C
      tseslint.configs.stylisticTypeChecked, #C
    ],                                       #C
    rules: {                                 #D
      "@typescript-eslint/no-non-null-assertion": "off",  #D
    },                                       #D
    languageOptions: {                       // #E
      parserOptions: {                       // #E
        projectService: true,                 // #E
        tsconfigRootDir: import.meta.dirname, // #E

    },                                       // #E

#A Enables type checking for this JavaScript file
#B Enables rules in eslint.configs.recommended for all files
#C Enables rules in tseslint.configs.strictTypeChecked and tseslint.configs.stylisticTypeChecked for TypeScript files
#D Disables typescript-eslint’s no-non-null-assertion rule
#E Tells ESLint how to communicate with the TypeScript type checker in this project

Using an @ts-check comment in a JavaScript file like this one gives valuable type feedback in your editor. Note that running tsc won’t report those type errors, since the file isn’t included in the build defined by tsconfig.json.

The configuration has two blocks. The first enables ESLint’s recommended rules, which you can find at eslint.org/docs/latest/rules. They’re valid for both JavaScript and TypeScript, so they apply to all files unconditionally. The second block enables two typescript-eslint rule sets, strictTypeChecked and stylisticTypeChecked; the -TypeChecked suffix means some rules need information from the type checker. Integrating type checking into ESLint takes extra configuration (visible in the same block) and makes linting slower, but it greatly expands the range of issues rules can cover.

Let’s try the new capabilities. Create condition-rules.ts:

Listing 2.9 — TypeScript with unnecessary conditionsTypeScript
const ninja = Math.random() > 0.5 ? "ryu" : "naruto";  #A
if (ninja === "ryu" || "naruto") {                    #B
  // Error: no-constant-condition                     // #B
}                                                        #B
if (ninja) {                                             #C
  // Error: @typescript-eslint/no-unnecessary-condition // #C
}                                                        #C
#A Defines a constant ninja with type "ryu" | "naruto".
#B This condition will always pass because it’s the “or” of two expressions, one of which is a constant.
#C This condition will always pass because all of ninja’s possible values are truthy.

Run the linter against the module:

$ npx eslint condition-rules.ts
/javascript-ninja-3e-code/ch4/eslint-project/condition-rules.ts
  3:5   error  Unexpected constant condition                    no-constant-condition
  3:24  error  Unnecessary conditional, value is always truthy  @typescript-eslint/no-unnecessary-condition
  7:5   error  Unnecessary conditional, value is always truthy  @typescript-eslint/no-unnecessary-condition

The first condition violates two rules: no-constant-condition from ESLint’s recommended set, and @typescript-eslint/no-unnecessary-condition from typescript-eslint’s strict set. (All rules outside ESLint’s core set are prefixed with a namespace.) The second condition violates only the typescript-eslint rule — because the first uses a pattern ESLint can identify as bad regardless of what ninja is, whereas the second only looks bad because the type checker knows ninja is always a non-empty string.

With these rule sets in place you’ll avoid many common traps. But there will be times when a rule works against you instead of for you, so next: finer-grained control.

2.2.2 Disabling ESLint rules

We enabled a broad range of rules from ESLint core and typescript-eslint — notably the “strict” and “stylistic” sets rather than the smaller “recommended” set. Those include many opinionated rules, which might conflict with code some developers consider perfectly fine.

Deciding which rules to enable is a challenge every ninja faces. More rules generally catch more errors and keep code style cohesive; on the other hand, it’s frustrating to write perfectly valid code and still get complaints from your tooling. Consider this example:

Listing 2.10 — TypeScript with unnecessary conditionsTypeScript
const dojoStudents = new Map([["Hidden Leaf", 2]]);   #A

const enrollNinja = (dojoName: string) => {
  if (!dojoStudents.has(dojoName)) {                        #B
    dojoStudents.set(dojoName, 0);                         #B
  }                                                            #B
  dojoStudents.set(dojoName, dojoStudents.get(dojoName)! + 1);   #C
};

enrollNinja("Hidden Leaf");
console.assert(
  dojoStudents.get("Hidden Leaf") === 3,
  "enrollNinja adds students to existing dojos.",
);

enrollNinja("Snake Way");
console.assert(
  dojoStudents.get("Snake Way") === 1,
  "enrollNinja adds students to new dojos.",
);
#A Creates a Map with the key Hidden Leaf mapped to the value 2.
#B Checks if the key dojoName exists in the map. If not, adds it with an initial value of 0.
#C Increments the value for dojoName. The ! after get(dojoName) is TypeScript’s non-null assertion operator.

The code is bug-free, but with the previous configuration the linter reports an error:

$ npx eslint enroll-ninja.ts
/javascript-ninja-3e-code/ch4/eslint-project/enroll-ninja.ts
  7:30  error  Forbidden non-null assertion  @typescript-eslint/no-non-null-assertion

The rule @typescript-eslint/no-non-null-assertion is part of the “strict” set. It forbids TypeScript’s non-null assertion operator because assertions about types can introduce human error into type checking. The problem: without the assertion, the checker will complain that dojoStudents.get(dojoName) could be undefined, when we know the preceding code guarantees a number.

There are a few ways to respond:

  • Rewrite the code to satisfy the rule.
  • Disable the rule for the project.
  • Make an exception to the rule using a comment.

It’s possible to rewrite the code to avoid the non-null assertion, but that isn’t always the best solution — so let’s look at the other two. To write non-null assertions freely, turn the rule off in the TypeScript block of eslint.config.mjs:

Turning the rule offES module
extends: [
  tseslint.configs.strictTypeChecked,
  tseslint.configs.stylisticTypeChecked,
],
rules: {
  "@typescript-eslint/no-non-null-assertion": "off",
},

The rule does have merit, though: even if you’re confident you’re using it correctly, the non-null assertion may worry anyone reviewing your code. For that reason it may be a good idea to accompany the operator with an explanatory comment — keeping the rule enabled and making exceptions case by case.

ESLint allows exceptions through “inline configuration”: comments in a specific format the linter recognises. The most common format for a one-line exception is: 

// eslint-disable-next-line [rule] [-- explanation]

Both the rule and the explanation are optional; with no rule specified, the linter ignores the next line completely. Here’s how you might disable the rule in this case (for a multi-line comment, the “next line” is the line after the comment):

An inline exception, with a reasonTypeScript
/* eslint-disable-next-line @typescript-eslint/no-non-null-assertion --
 * The previous condition ensured that dojoStudents.get(dojoName) exists.
 */
dojoStudents.set(dojoName, dojoStudents.get(dojoName)! + 1);

That satisfies the linter and explains to readers why an exception is warranted. So far every rule has been aimed primarily at avoiding bugs — but that isn’t all ESLint is good for.

2.2.3 Enforcing a distinctive code style

In 2008 Douglas Crockford wrote JavaScript: The Good Parts, arguing that developers should ignore some of the language’s more esoteric features and focus on a subset that produces readable, maintainable code.

Since then ECMAScript has added more and more features (and deprecated a few Crockford complained about, such as the notorious with). With more features comes more complexity: a new feature may make a task easier, but it also means more possible ways to implement it, adding cognitive overhead for those writing and reviewing code.

ESLint rules act as a counterweight. By discouraging certain patterns they make it easier to focus on the “good parts” and write clearer code. Developers will always differ on exactly which patterns those are — but once a team decides to disallow a pattern, an ESLint rule makes that decision much easier to enforce.

Some style rules live in the core ESLint and typescript-eslint sets. One core rule is no-shadow, which forbids “shadowing”: defining a variable with the same name as one in the outer scope.

Listing 2.11 — Shadowing a variableJavaScript
const count = 10;                                 #A
console.log("Outer count:", count);

for (let count = 0; count < 3; count++) {      #B
  console.log("Inner count:", count);              #C
}

console.log("Outer count still:", count);
#A Defines a variable named count in the scope of the module.
#B Defines a variable named count in the scope of the for loop.
#C References the loop’s count, which shadows the module’s count.

Shadowing is legal in JavaScript, but bad for readability: readers may struggle to track which variable is referenced at any given point. Although ESLint ships no-shadow, it isn’t in the recommended set, because some developers prefer not to have to invent unique variable names when such a conflict occurs. To use it you have to enable it yourself (or use a third-party config that includes it):

Enabling no-shadowES module
// In your project’s ESLint config
rules: {
  "no-shadow": "error",
}

Beyond ESLint and typescript-eslint core, plugins offer all kinds of style rules. Prolific developer Sindre Sorhus has strong opinions, codified in eslint-plugin-unicorn — a grab bag of more than 100 rules, including:

  • Rules enforcing common JavaScript conventions, like supplying a message string when creating an Error.
  • Rules enforcing a uniform style, like having all filenames use the same casing convention.
  • Rules enforcing opinions on the “good parts”, such as forbidding the use of null.

That’s a taste of what’s possible — there’s a whole world of ESLint plugins to explore. And if you can’t find one that does what you want, you can always write your own rule, as Chapter 15 discusses.

2.3 Automating formatting with Prettier

No one likes code that runs on and on like a run-on sentence, forcing readers to scroll horizontally, struggling to match up braces, wishing the author had thought more about formatting.

In its infancy ESLint offered a simple line-length rule, but it put the burden on developers to figure out how to get under the limit, and teams spent hours arguing about approaches.

Those dark days are gone thanks to Prettier, which describes itself as “an opinionated code formatter” — and its opinionated nature made it enormously popular. Where ESLint offers an endless assortment of rules, Prettier has only a handful of configuration options, which most teams consider a blessing. The old arguments have largely given way to an accepted compromise: just use Prettier.

2.3.1 Setting up Prettier

Create a new directory with an empty package.json so npm can track dependencies:

$ echo "{}" > package.json

$ npm install --save-dev prettier

$ echo "{}" > .prettierrc

2.3.2 Running Prettier from a commit hook

The best way to use ESLint and Prettier is continuously, via editor integration. With the right extensions, ESLint’s auto-fixes and Prettier’s formatting apply every time you save, so you never have to think about formatting — you can focus on behaviour.

But you can’t assume collaborators work the same way. That’s where Husky comes in: it uses git’s pre-commit hook to run scripts against code changes automatically. Install it as a dev dependency in the Prettier project: 

$ npm install --save-dev husky
$ npx husky init

Looking at package.json, there’s now a prepare script:

package.jsonJSON
// In package.json
"scripts": {
  "prepare": "husky"
}

prepare is one of npm’s “lifecycle scripts”. Like any script it can be run manually with npm run prepare, but it also runs automatically when a user performs npm install with no arguments. Since that’s usually the first thing someone does when starting work on a package, it’s a great place for setup code. Here the setup configures the git repo to use .husky as its hooks path (see git-scm.com/docs/githooks to learn more about hooks).

That default prepare script won’t work if package.json isn’t at the root of the git repository. In the book’s official repo, for instance, the Prettier project sits in ch4/prettier-project. To handle that, change prepare to run an external shell script, prepare.sh:

package.jsonJSON
// In package.json
"scripts": {
  "prepare": "sh prepare.sh"
}

Extracting complicated npm scripts into separate script files is always a good idea — it makes both the script and package.json more readable. Create prepare.sh:

Listing 2.14 — A shell script to prepare Husky from a subdirectoryshell
#!/bin/env bash                              #A
PROJECT_PATH=$PWD                            #B
cd "$(git rev-parse --show-toplevel)"        #C
husky "$PROJECT_PATH/.husky"                 #D
#A Standard shebang to tell the OS to run this as a bash script.
#B Obtain the path this script was run from and store it as PROJECT_PATH.
#C Navigate to the root of the git repo.
#D Tell Husky to change the git repo’s hooks path to the project’s .husky directory.

With that script in place, run npm run prepare to apply it. Confirm the change with git config core.hooksPath — the hooks path should now be the .husky directory created by husky init.

The shell script created in .husky/pre-commit now runs on every commit. Set it up to run Prettier:

Listing 2.15 — A pre-commit script to format filesshell
#!/bin/env bash
cd "$(dirname "$(readlink -f "$0")")/.."      #A
prettier . --write                            #B
git update-index --again                      #C
#A Navigate to this script’s parent directory, which should be the project root.
#B Use Prettier to format all files in the project.
#C Tell git to include any changes Prettier made to the files staged for this commit.

Done! Now whenever anyone commits, their changes are formatted first — unless they deliberately bypass the hook, for instance with git commit --no-verify.

Formatting every file on every commit isn’t ideal in large projects, so there’s lint-staged, which pairs with Husky to run scripts against staged files (or even staged parts of files) only.

That’s only the surface of Husky. As well as modifying staged files, the pre-commit hook can abort a commit by exiting with a non-zero code — a convenient way to run static analysis like TypeScript and ESLint, or unit tests like Vitest.

But be careful of the tradeoff: the more the pre-commit hook does, the slower it gets, adding friction when people contribute — especially with type checking, since TypeScript can’t analyse types in staged files independently of the whole project, so it always takes significant time, even with lint-staged. For that reason large projects avoid running TypeScript (or typescript-eslint) in a pre-commit hook and defer those tasks to CI after a commit is pushed.

  2. TypeScript adds types to JavaScript, allowing many of the most common coding mistakes to be caught early.
  3. ESLint lets you enforce a wide range of customisable coding rules, ranging from error-catchers to stylistic standards.
  4. The typescript-eslint plugin provides TypeScript’s type information to ESLint, opening up many more rules at the expense of linting speed.
  5. Prettier automates code formatting, neatly breaking up long lines and applying consistent indentation.

Chapter 3

Working with Node.js and npm

This chapter covers

  • How Node.js works
  • Managing dependencies with npm
  • Using JavaScript as a system-level scripting language

In 2009 Ryan Dahl announced Node.js. His goal was a system that would operate more efficiently than the venerable Apache HTTP server thanks to non-blocking IO — a strategy that keeps the CPU from sitting idle while waiting on the disk or the network. To do that he needed a language in which asynchronous server logic is straightforward to write. JavaScript, he realised, was the perfect fit.

Today Node.js has grown beyond its origins into a major platform, not just for servers but for applications of all kinds. The secret to its success is the language itself, which proved far more versatile than its humble browser beginnings suggested.

This chapter covers creating and managing JavaScript projects with Node.js and npm. Many of the topics apply to every kind of JavaScript project, even browser-targeted ones: whatever the runtime, Node.js and npm manage dependencies, run tests and build code for production.

Setup and alternatives

The chapter has hands-on exercises requiring Node.js in your development environment, so you can run the node, npm and npx commands. Step-by-step installation and version-management instructions are in Appendix A.

Appendix A also covers alternatives to Node.js and npm. The book uses Node.js and npm throughout whenever JavaScript runs outside the browser, but for your own projects consider the alternatives — in particular pnpm, which offers several advantages over npm for large projects.

3.1 The Node.js runtime

To understand Node.js, look at the problem Ryan Dahl was trying to solve.

Imagine a server with blocking IO receiving a request for /index.html and returning the file’s contents. The request handler might look something like this:

Blocking IO — the wasteful versionJavaScript
function indexHandler(req, res) {
  const html = readFile("index.html", "utf8");
  res.send(html);
}

This straightforward-looking code glosses over a big waste of resources: the CPU sits idle for thousands of cycles while the file contents are read, leaving other requests waiting. Web servers like Apache use threads to mitigate that inefficiency, letting the CPU be interrupted mid-task and assigned to another — but threads add overhead of their own.

Under Node.js, the request handler might look like this instead:

Non-blocking IO with a callbackJavaScript
function indexHandler(req, res) {
  fs.readFile("index.html", "utf8", (html) => {
    res.send(html);
  });
}

This code, like all JavaScript, runs in a single thread — so only one part of the program can run at a time. But it uses a callback, a function passed as an argument to fs.readFile and invoked when the read completes. That leaves the CPU free to handle other requests until then.

Note Because JavaScript is single-threaded, callbacks like the one above are “blocked” until all JavaScript code has finished executing. One of the most important tenets of JavaScript performance is: don’t block the thread! Chapter 17 shows how long computations can be delegated outside the thread using workers.

In recent years it has become more common to express this logic with promises instead of callbacks, especially with the async/await syntax added in ES2017 — the same non-blocking behaviour without complicating the code with nested functions:

The same handler with async/awaitJavaScript
async function indexHandler(req, res) {
  const html = await fsPromises.readFile("index.html", "utf8");
  res.send(html);
}

Chapter 8 goes deeper on promises and async/await. For now, on to some hands-on coding.

3.1.2 Using Node.js APIs

Node.js offers an extensive set of APIs, documented at nodejs.org/docs/latest/api. Let’s use some of them for a simple project: a command-line calculator. Start with a project directory containing a single file, index.mjs:

Listing 3.1 — A calculator program in Node.jsES module
import * as readlinePromises from "node:readline/promises";  // #A
import { stdin, stdout } from "node:process";            // #B

const rl = readlinePromises.createInterface({
  input: stdin,
  output: stdout,
});

while (true) {
  const input = await rl.question('Enter expression or ".exit":\n> ');  // #C
  if (input === ".exit") {
    rl.close();
    break;
  } else {
    console.log(eval(input));                                  // #D
  }
}
#A The import * syntax creates an object containing all exports from the specified module — here "node:readline/promises".
#B The import { stdin, stdout } syntax takes the two specified exports and assigns them to variables with the same names.
#C The await keyword effectively pauses the program until it receives a line of input. Chapter 8 explains how this syntax works.
#D The eval function executes the given string as JavaScript code. Never use eval with untrusted user input!

The program uses the readline API to read a line of input. Node.js offers readline in two flavours — callback-based and promise-based — and the promise-based one is generally considered more modern and convenient, so that’s what’s used here (promises are covered in detail in Chapter 8).

What is the .mjs extension?

When Node.js was created it used a module standard called CommonJS. Later, a new standard known as ECMAScript Modules (ESM) was incorporated into the ECMAScript spec itself, and much of the ecosystem has transitioned from CommonJS to ESM.

Node.js has supported both since v12.17.0, but for backward compatibility it treats .js files as CommonJS by default. The .mjs extension tells Node.js the file should be treated as an ESM — as is the case with all code in this book.

In general require is associated with CommonJS while import is associated with ESM; Chapter 14 compares the standards in depth.

As a follow-up, try restricting the input to a subset of characters so users can enter calculations but not execute arbitrary JavaScript on your system. That’s a good use case for regular expressions (Chapter 13).

3.2 Managing Node.js dependencies

In its original life as a browser scripting language, JavaScript had no notion of dependencies. Node.js changed that: it popularised the concept of modules — JavaScript files that run in their own namespace — and introduced the convention of a node_modules directory that modules could load each other from without specifying a complete file path.

Shortly after Node.js appeared, Isaac Schlueter created a Node.js package manager called simply npm, along with a public registry. Together those innovations made sharing JavaScript code dramatically easier.

Even on a web application there’s a good chance you’ll use Node.js and npm to manage dependencies and prepare code for deployment; building code for the web is covered in Chapter 14.

3.2.1 Installing dependencies with npm

Create a directory called http-server and run:

$ npm init -y

This creates a skeletal package.json. (Without the -y flag it would have prompted for information to fill in some of the blanks.)

The generated package.jsonJSON
{

  "version": "1.0.0",
  "main": "index.js",          // #B
  "scripts": {                  // #C
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC",
  "description": ""
}
#A npm inferred the name from the current directory.
#B The entry point for the project. Entry points are explained when we discuss node_modules.
#C Package scripts are very useful — see the scripting section of this chapter.

Most of the initial fields are metadata we can ignore, since we don’t intend to distribute this package. For now package.json matters for one reason: saving dependencies.

Node.js provides low-level HTTP APIs, but very few projects use them directly; instead they use open-source packages that make those APIs easier. One of the most popular is express, a simple and extensible web server framework. Install it and see what happens: 

$ npm install express@5

npm connects to the public registry and downloads the package with the specified name and version. Then the real work begins: it recursively downloads that package’s dependencies, and theirs, until the dependency tree is complete. The fruits of that labour appear in the project’s new node_modules directory, containing all the downloaded packages — plus a new package-lock.json describing the contents of node_modules.

Looking at package.json, it now lists the new dependency:

The exact version you see will likely be newer, reflecting the latest available in the registry. That ^ prefix is explained in Section 3.2.3. First, some code that uses the new dependency — create index.mjs (note the .mjs extension, indicating an ESM module):

A minimal Express serverES module
import express from "express";

const app = express();

  res.send("Hello, dependencies!");

const PORT = 3000;
app.listen(PORT, () => {
  console.log(`Now listening at http://localhost:${PORT}`)
});

Run it to start the server:

$ node index.mjs

Open http://localhost:3000 in a browser to confirm it’s running. When you’re done, press Ctrl+C in the terminal to send a SIGINT signal, causing Node.js to exit.

You’ve now installed a dependency from the npm registry and used it in code. Next: how that import statement actually works.

3.2.2 Understanding node_modules

In Node.js code you’ll typically see three kinds of import statements:

  • Imports that reference a core Node.js API, with or without the node: prefix.
  • Imports that use a relative file path prefixed with ./ or ../.
  • Imports that start with a package name.

An import name that starts with a package name is a bare specifier. When Node.js meets one, it searches for the closest node_modules directory containing that package: starting from the directory containing the importing module, it checks ./node_modules/<package>, then ../node_modules/<package>, and so on up to the filesystem root.

Note Resolving bare specifiers by searching node_modules is Node.js’s default behaviour, but it can be overridden. Yarn and pnpm offer a “Plug’n’Play mode” in which the package manager tells Node.js to resolve external dependencies directly from a central cache. That has advantages for build performance and security, but can confuse IDEs and other tooling that expect dependencies in node_modules.

Once the package directory is found, Node.js looks for the package code’s entry point. The rules are:

  1. If package.json has an exports field, Node.js tries to map the import statement to the corresponding export. The field is quite versatile — specifics are in Chapter 14.
  2. If exports is not defined and the import statement includes a file path, Node.js uses that path relative to the package directory as the entry point. For example import "package/lib/module.js" resolves to lib/module.js inside the package.
  3. If exports is not defined and the import has no file path, Node.js uses the entry point defined by main in package.json.

This resolution algorithm lets multiple versions of the same package coexist in one project — which happens frequently with indirect dependencies. Suppose your project depends on dep1 and dep2, but dep1 depends on lodash@3 while dep2 depends on lodash@4. Both can be satisfied by structuring node_modules like this:

Nested node_modules for conflicting versionstree
node_modules/
  dep1/
    node_modules/
      lodash/     # contains lodash@3
  dep2/
    node_modules/
      lodash/     # contains lodash@4

This works because import statements in dep1 and dep2 load lodash from their respective node_modules directories. Note that importing lodash in your own project’s index.mjs would fail to resolve.

Happily npm handles all this automatically, creating nested node_modules directories for indirect dependencies as needed. It also reduces duplication by hoisting indirect dependencies to the top level when there are no conflicting version requirements — so if dep1 and dep2 both depend on the same lodash version, the tree looks like this:

Hoisted, deduplicated treetree
node_modules/
  dep1/
  dep2/
  lodash/

Importing code from local packages

Import another module from your package with a relative path; import a dependency installed with npm by package name. But what if you want to import a module from another package on your system?

The standard solution is a symlink in node_modules so you can treat it as a dependency. npm offers two ways:

  • If you’re working on one of your project’s dependencies, run npm link <dependency-dir> to add a symlink to that package’s directory in node_modules.
  • If your project involves multiple interdependent packages, declare a workspaces list in package.json, which tells npm to create symlinks for all of those packages in node_modules when you run npm install. The packages can then import one another.

3.2.3 Syncing and updating dependencies

In npm’s early days developers faced a conundrum: checking the entire node_modules tree into version control created large diffs whenever a dependency changed, but the alternative risked inconsistencies whenever the project was installed elsewhere, because the dependency list in package.json didn’t contain enough information to reconstitute the same tree.

The solution was a lockfile, package-lock.json. When a user downloads a project and runs npm install, npm uses the lockfile to reconstitute the exact same node_modules tree. Today the norm is to commit package-lock.json but not node_modules, which keeps teams in sync with minimal effort. npm even has built-in merge conflict resolution for the lockfile: if you hit a conflict in package-lock.json, just run npm install.

Note JavaScript developers are divided on whether to use package-lock.json in packages consumed by others. Doing so freezes your package versions during development but doesn’t affect the downstream project, which can cause drift. As Sindre Sorhus put it: “If you use a lockfile for packages, your local dependency tree will not match the dependency tree of users having your package as a dependency.”

Having dependencies in both files confuses people: what’s the purpose of each? The key reason is that the lockfile rigidly specifies the exact version of every dependency in the tree, while package.json allows version ranges — which provide a smooth path for routine updates.

Take another look at the dependencies list in the http-server project:

package.json dependenciesJSON
"dependencies": {
  "express": "^5.1.0"
}

When we told npm to install express we only specified a major version. npm’s default behaviour is to find the latest exact version matching the specifier, then prefix the version in package.json with ^, creating a caret range.

To understand caret ranges you first need semver (“semantic versioning”). Each version has three components:

<major>.<minor>.<patch>

A version may also have a pre-release tag appended with a hyphen: 1.0.0-beta.1 is a pre-release considered earlier than 1.0.0.

The key to semver is the convention that incompatible changes must come with a newer major version number (pre-releases and versions below 1.0.0 are exceptions). As long as package authors honour that convention, newer minor and patch versions of the same dependency are safe to install.

That’s what the caret range means: it covers all newer but compatible versions, so you benefit from bug fixes and improvements. With "express": "^5.1.0", both express@5.1.1 and express@5.2.0 are compatible, but express@6.0.0 is not. (There’s a neat tool at semver.npmjs.com for trying out range specifiers and seeing which versions they cover.)

To update a package to the latest version within the range in package.json, use npm update --save <package>. The update command installs the new version in node_modules and revises the lockfile, while --save also modifies package.json to indicate the new version as the minimum.

To get the latest release regardless of the range, use npm install <package>@latest. Note that install saves its changes to package.json by default while update does not — which is why the --save flag is recommended when updating, so you keep a clear, readable record of all version changes.

3.2.4 Forking and patching dependencies

One great virtue of open source is that you’re free to change any dependency you use, fixing bugs or adding features without seeking the maintainers’ approval.

The traditional mechanism is to fork: create a full copy of the package’s repository, then apply your changes to the source. Most packages list their repository in package.json metadata, viewable with npm view <package> or by searching npmjs.com. Once you’ve forked, replace the version string in package.json with a direct git link to your fork:

Pointing at a forkJSON
"dependencies": {
  "express": "git+ssh://git@github.com:trevorburnham/express#5.1.0"  // #A
}
#A The # suffix indicates a git tag, which in this case points to a release version.

When you run npm install, npm downloads the repo, runs its build script (if defined) to generate the package artifacts, and adds them to node_modules as if it had downloaded the package from the registry.

Forking makes sense if you want to maintain a differentiated copy, but suppose you just want a quick bug fix while waiting for the maintainers to merge your pull request — or you need to change an indirect dependency. Editing code in node_modules directly isn’t stable: the change isn’t in version control, collaborators don’t receive it, and npm may overwrite it. The solution that persists patches is patch-package.

First install it as a dev dependency:

$ npm install --save-dev patch-package

The --save-dev flag adds the package to the devDependencies section instead of dependencies, differentiating what’s needed at runtime from what’s only needed in development. When you install a package, its transitive dependencies are installed but its transitive devDependencies are not.

Make your changes in node_modules, then run:

$ npx patch-package <package>

(The npx command runs binaries from packages — more in Section 3.3.2.) This generates a .patch file with your changes, which you can check into version control. To make sure the patch is applied every time npm installs that package, add a postinstall entry to the scripts section of package.json:

package.jsonJSON
"postinstall": "patch-package"

The postinstall script runs automatically after npm install and other commands that install packages into node_modules; lifecycle scripts are covered in section 3.3.1.

That’s dependency management, including changing dependencies via forking and patching. Next: how Node.js and npm can be used to write all kinds of scripts, from project automation to system management.

3.3 Scripting with Node.js

Once Node.js freed JavaScript from the confines of the browser, many developers discovered it was the only language they needed. They began using it for tasks that previously required a foray into shell scripting or firing up a Python or Ruby interpreter.

This section looks at several approaches to running scripts with Node.js, and at how to distribute scripts in an npm package anyone can run with a single command.

3.3.1 Defining scripts in package.json

The scripts section of package.json is a simple way to define short scripts:

package.jsonJSON
"scripts": {
  "hello": "echo 'Hello, scripts!'"
}

To execute a script, use npm run <script>:

$ npm run hello
Hello, scripts!

You can pass additional arguments, which get appended to the script. Use the -- separator before them so they aren’t treated as arguments to npm itself: 

$ npm run hello -- "And goodbye."
Hello, scripts! And goodbye.

A few script names have special rules:

  • The test, start, restart and stop scripts can be run with the shorthand npm <script> instead of npm run <script>.
  • If a script name starts with pre/post, it runs before/after the matching script. With prebuild, build and postbuild defined, npm run build runs all three in order.
  • Several npm commands trigger life cycle scripts: preinstall and postinstall run before and after npm install. Consult the npm documentation for details.
  • The prepare script runs automatically whenever the package is installed in another package — a common use case being compiling binaries.

One of the most powerful features is that npm puts every executable exported by the project’s installed packages on the PATH for scripts. A project with a dev dependency on ESLint might have:

package.jsonJSON
"scripts": {
  "lint": "eslint ."
}

Scripts can also use npm run to trigger other npm scripts:

package.jsonJSON
"scripts": {
  "lint": "eslint .",
  "build": "npm run lint && ./build.sh"
}

3.3.2 Writing executable scripts with Node.js

Node.js supports the shebang syntax (so called because the two characters #! are the “sharp” and “bang”), letting Mac/Linux systems treat a JavaScript file as an executable. Create hello.mjs:

hello.mjsES module
#!/usr/bin/env node
console.log("Hello, execution!");

Then chmod +x hello.mjs to give the file executable permissions. Now you can run it with ./hello.mjs instead of node hello.mjs.

However the script is run, Node.js resolves any import statements with the node_modules algorithm relative to the script’s location — so including dependencies is straightforward if the script ships as part of an npm package.

Node.js has several built-in APIs in its child_process namespace for calling arbitrary system commands, but they’re very verbose, requiring several parameters even for simple cases. Several npm packages therefore offer a more succinct syntax. One of the most popular is Google’s zx, which provides a function named $ that calls any shell command:

A script using zxES module
#!/usr/bin/env node
import { $ } from "zx";

const { stdout: dirContents } = await $`ls`;
console.log(
  dirContents.split("\n").includes("package.json")
    ? "Yes, this dir contains a package.json file."
    : "No, this dir does not contain a package.json file.",
);

Suppose you want to run a Node.js script where installing npm dependencies is impractical — a CI process with a firewall blocking the npm registry, for instance. In that case use a bundler such as esbuild to create a single JavaScript file containing the script and all its dependencies. Chapter 14 looks at esbuild more closely.

3.3.3 Running package executables with npx

Section 3.2.1 showed how npm packages provide entry points so import statements can reference their code once installed in node_modules. But packages aren’t limited to code: it’s common for them to distribute executables that can be run from the command line.

Typically such an executable is a JavaScript file written as described in Section 3.3.2. To make it an executable, add a bin entry to package.json:

package.jsonJSON
"bin": {
  "my-command": "bin/my-command.js"
}

When npm installs the package with that declaration, it creates an executable called my-command linked to the package’s bin/my-command.js. Once installed, the executable can be run from package.json scripts.

You can also run package executables directly with npx, a command bundled with npm. If ESLint is installed, npx runs its eslint executable without creating a scripts entry: 

$ npx eslint .

But npx’s power goes far beyond that. When you run npx <command> for a command that doesn’t match an executable in the local project, npx checks the registry for a package with that name. If it finds one, and if one of that package’s executables has the same name as the package (or it defines only one executable with any name), it temporarily installs the package and runs that executable.

Running a package executable straight from the registry is enormously convenient for packages you don’t need often, because it avoids the overhead of adding them to your node_modules tree and lockfile.

3.4 Summary

  1. Node.js is a popular JavaScript runtime that provides APIs for the file system, networking and other OS interactions.
  2. JavaScript code always runs in a single thread. Callbacks and promises allow I/O operations to be performed asynchronously, keeping the JavaScript thread unblocked.
  3. npm installs packages into a node_modules directory containing a project’s entire dependency tree, saves top-level dependencies in package.json, and uses package-lock.json to track the full contents of node_modules for version control.
  4. Bare specifiers — imports using a package name rather than a complete file path — are resolved by recursing through the closest node_modules directory.
  5. Node.js supports executable scripts with the shebang syntax, and packages can make executables available by declaring them in the bin field of package.json.
  6. npx runs executables from other packages; if the specified package isn’t installed, it’s downloaded from the registry and temporarily installed while the command runs.
